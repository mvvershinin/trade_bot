# Проверки: тесты, линтер, типы

Как гонять и сколько это стоит. Замеры 04.09.2026, машина владельца счёта, 12 ядер.
Часть чисел обновлена позже — дата стоит рядом с каждым замером, а не только здесь:
дерево быстро меняется, несколько исполнителей правят тесты параллельно, и следующий
прогон легко даст другое число. Смысл чисел — порядок величины и направление
(растёт/падает), а не точное совпадение.

## Повседневный цикл

**После правки:**

```
.venv/bin/pytest -n auto -q -m "not slow"
```

**16–20 с** против 35–41 с полного (замер 06.09.2026, `test-expert`, машина
под нагрузкой от трёх параллельно работающих исполнителей; в спокойной копии
дерева — 16,1–16,7 с против 38,0–39,5 с). Отбрасывается **41 узел из 3473**:
сверка с прототипом, запуск команд подпроцессом, тяжёлая отрисовка Qt.

⚠️ **«5-10 секунд» из прежней редакции этого документа не выходит и не выйдет.**
Та цифра была написана без замера. Последовательно быстрый набор идёт около 90 с
против 170 с полного; всё, что быстрее, даёт параллель, а не разметка.

История: до 06.09.2026 эта команда была фикцией — маркеров в дереве не было
ни одного, `-m "not slow"` не отсекал ничего (`D-081`). Разметка сделана
`test-expert` 06.09.2026 по замеру
[`.docs/quality/test-durations-2026-09-06.md`](quality/test-durations-2026-09-06.md);
чтобы фикция не вернулась молча, стоит сторож `tests/test_slow_markers.py`.

**При отладке падающего теста:**

```
.venv/bin/pytest -x --lf          # только вчерашние падения, стоп на первом
.venv/bin/pytest --ff             # известно-плохие первыми, дальше остальные
.venv/bin/pytest --sw             # грызть красный сюит по одному
.venv/bin/pytest путь::имя_теста  # один конкретный
```

`--lf` и `--ff` — часть pytest, плагинов не требуют, состояние хранится в его кеше.

**Перед коммитом — полный:**

```
.venv/bin/ruff check . && .venv/bin/mypy && .venv/bin/pytest -n auto
```

**Периодически — поиск медленных:**

```
.venv/bin/pytest --durations=10 --durations-min=1.0
```

Не на каждый прогон. Раз в неделю или когда прогон заметно вырос.

## Маркеры

Объявлен **один** маркер, и ровно потому, что он расставлен:

```toml
[tool.pytest.ini_options]
markers = [
    "slow: дольше 0,5 с — сверка с прототипом, запуск команды подпроцессом, тяжёлая отрисовка Qt; в повседневный прогон не входит",
]
```

`unit` и `integration` из прежнего плана **специально не объявлены**: маркер,
который никто не ставит, — это ровно то, чем был `-m "not slow"` до 06.09.2026.
Появится расстановка — появится строка.

**Порог 0,5 с выбран по замеру**, а не назначен: p95 теста этого дерева — 0,12 с,
p99 — 0,81 с; порог ловит 29 функций (41 узел, 1,2 % набора) и снимает 45 %
времени. Порог 0,25 добавил бы 36 функций ради ещё 7 % времени, порог 0,1 —
172 функции ради 15 %. Разбор, распределение по файлам и таблица «что купил
каждый порог» — [`.docs/quality/test-durations-2026-09-06.md`](quality/test-durations-2026-09-06.md).

`--strict-markers` стоит в `addopts`: опечатка (`@pytest.mark.slowe`) роняет
прогон, а не проглатывается молча.

**Четыре теста перешагивают порог и остаются в быстром наборе намеренно** —
сторожа, читающие дерево целиком (латиница в именах, границы слоя `app`,
виджет без `QApplication`, экран дочернему процессу). Вместе 3,04 с, 1,9 %
прогона. Список лежит в коде — `STAY_FAST` в `tests/test_slow_markers.py`, —
и проверяется: разметить исключённый тест прогон не даст.

**Сторож против возврата фикции** — `tests/test_slow_markers.py`, десять
проверок, каждая проверена мутацией. Он падает, если разметку снесли,
если `slow` перестал объявляться, если метка ушла с самого дорогого файла
и если отобранное pytest разошлось с написанным в исходнике.

## Параллельный прогон

`pytest-xdist` **установлен** 06.09.2026 по просьбе владельца счёта, версия 3.8.0.
Если после пересоздания окружения `-n auto` откажет неизвестным аргументом — значит
пакет пропал, ставить заново:

```
.venv/bin/pip install pytest-xdist
```

Дальше `-n auto` — по числу ядер. Замер 06.09.2026: полный прогон ~31–35 с против
~175 с последовательно на нынешних 3432 тестах — в разы быстрее.

**Когда мешает:** если тесты делят состояние — файл, порт, базу. Параллель не создаёт гонки,
она вскрывает существующие. Упало под `-n auto`, но проходит последовательно — значит гонка
есть и её надо чинить, а не отключать параллель. Так уже было: `test_from_status_scrubs_the_body_it_is_handed`
падал в одиночку и проходил в компании соседей (`BACKLOG.md`, `D-078`, закрыто 06.09.2026).

Тесты одного класса или модуля можно держать в одном процессе: `--dist loadscope`.

## 575 замечаний ruff и 185 ошибок mypy

Замер 06.09.2026 (координатор); было 536 и 155 на 04.09.2026.
Это разобранный остаток, не мусор. Но пока прогон красный, он **не даёт сигнала**: новую
ошибку не отличить от старой.

**Порядок разбора ruff:**

```
.venv/bin/ruff check . --statistics       # какие коды и сколько раз — начинать с частых
.venv/bin/ruff check . --fix              # безопасные автоправки (57 штук)
.venv/bin/ruff check . --fix --unsafe-fixes  # ещё 14, каждую посмотреть глазами
```

Остаток заморозить: коды нарушенных правил вынести в `ignore`, включать обратно по одному
по мере разбора. Нативного baseline у ruff нет — issue открыт с 2022 года.

Альтернатива: `ruff check --select КОД --add-noqa .` — проставить `# noqa` на текущие
нарушения одного правила. Тогда правило начинает работать на новый код, а старый молчит.
В этом проекте есть встречное требование: подавление обязано называть код и причину
(`PGH004`), голый `# noqa` запрещён — значит `--add-noqa` без ручной доработки не подходит.

**Порядок разбора mypy** — есть устоявшийся паттерн, `mypy-baseline`: снимок текущих ошибок,
CI падает только на новых. Либо через конфиг:

```toml
[tool.mypy]
ignore_errors = true

[[tool.mypy.overrides]]
module = ["engine.*", "strategies.*"]
ignore_errors = false
```

Чистые модули включаются по одному. Флаги строгости добавляются в порядке: `warn_unused_configs`
→ `warn_redundant_casts` → `warn_unused_ignores` → `disallow_untyped_defs`.

**Это отдельная задача, а не условие работы.** Красный прогон линтера не блокирует разработку
и не повод останавливаться.

## Девять падающих тестов — запись устарела

На 04.09.2026 в `test_app_live_feed.py` были красными девять тестов (список ниже —
для истории), с реальными ожиданиями сокета по три секунды на тест.

⚠️ **Проверено 06.09.2026, но не перезапуском команды — доступа к запуску тестов
в этом проходе не было.** Два признака, оба косвенные: (1) полный офскрин-прогон
`test-expert` (`-n 4`) дал `3425 passed, 1 skipped, 0 failed`, падений нет вовсе
(`.docs/quality/test-registry-2026-09-06.md` §5); (2) в файле те же по имени тесты
сегодня ждут `await asyncio.sleep(0.02)`, а не многосекундное настоящее ожидание
сокета, — код, из-за которого держалась старая причина падения, заменён.

Список сохранён для истории, а не как текущий красный прогон:

```
test_a_refused_snapshot_is_neither_written_nor_counted_and_is_said_once
test_a_minute_with_nothing_accepted_is_not_written
test_the_link_is_reconnecting_between_attempts_and_offline_only_when_taken_down
test_a_refusal_that_a_retry_cannot_fix_takes_the_stream_down
test_an_outage_is_retried_and_its_reason_is_said_once[failure0]
test_an_outage_is_retried_and_its_reason_is_said_once[failure1]
test_start_on_a_running_stream_does_not_open_a_second_socket
test_a_restart_right_after_stop_waits_for_the_old_socket_to_close
test_switching_on_again_reuses_the_session_and_restarts_the_stream
```

Если прогон снова покраснеет на этом файле — заводить новую запись с датой, а не
считать, что вернулись те же девять: причина, описанная здесь (настоящий сокет),
в коде уже не видна, значит и падение будет по другой причине.

Отдельная, ещё не закрытая находка того же файла — `D-017`: дублёр `FakeWorker`
не отвечает на все вызовы, которых просит `app/backfill.py`, и догрузка в тестах
падает в лог, а не в прогон.

## Что писать в новых тестах

**По умолчанию — юнит с подменой зависимостей.** В проекте для этого уже есть `Protocol`
в `engine/ports.py`: `CandleSource` и `OrderExecutor`. Движок проверяется на поддельном
источнике и поддельном исполнителе, без базы и без Qt.

**Интеграционный — только когда проверяется именно стык.** Настоящая SQLite нужна тесту
хранилища, живой Qt — тесту виджета. Всему остальному не нужны ни та ни другой.

Соотношение на 06.09.2026 (замер test-expert) — 61 183 строки тестов на 56 674 строки
кода (было 28 730 на 26 638 на 04.09.2026 — оба выросли примерно вдвое за пару дней
активной работы), и по-прежнему ни одного `unittest.mock` на весь проект: вместо
подмен поднимаются настоящие компоненты. Так больше не делать.
