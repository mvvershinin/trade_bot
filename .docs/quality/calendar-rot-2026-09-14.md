# Протухание сторожей по календарю — замер 14.09.2026

Повод: четыре красные проверки на бегунке GitHub (прогон 34834947367), `B-049`.
Вопрос замера: сколько в сюите сторожей, которые зеленеют в день написания
и краснеют сами по себе, когда наступает нужная дата.

---

## 1. Чем мерили

Сдвинуть часы **всему процессу**, не трогая ни строки кода и ни одного импорта.
Перехват трёх системных вызовов через `LD_PRELOAD` (`clock_gettime`, `time`,
`gettimeofday`), сдвиг задаётся переменной `CLOCK_SHIFT_DAYS`. Монотонные часы
не трогаются — сроки и таймауты работают как обычно.

Исходник — `.docs/quality/tools/shiftclock.c`, собирается одной командой:

```
gcc -shared -fPIC -o shiftclock.so shiftclock.c -ldl
CLOCK_SHIFT_DAYS=137 LD_PRELOAD=$PWD/shiftclock.so .venv/bin/pytest -q -m "not slow" -n auto
```

## 2. Чем мерить не вышло, и почему это важнее самого замера

Первый инструмент был на Python: подменить `datetime` и `date` в модулях проекта
на подклассы со сдвинутым `now()`. Он дал **488 падений** — картина катастрофы.

Контрольный прогон тем же инструментом со сдвигом **ноль дней** дал **485 падений**.
То есть 485 из 488 — следствие подмены класса, а не сдвига времени: подкласс `datetime`
ломает сравнения типов, `dataclass` и всё, что смотрит на `type(...)`. Настоящий сигнал
был три проверки из четырёхсот восьмидесяти восьми, и ровно этот шум выдал бы отчёт
«полсюиты держится на календаре» — вывод, ложный примерно во столько же раз, во сколько
шум превышал сигнал.

**Что отсюда следует для любого замера:** инструмент, который сам не прогнан
с нулевым воздействием, показывает собственную поломку и выдаёт её за находку.
Контроль стоил одного прогона — двадцать одну секунду.

## 3. Что намерено

Сюита после починки `B-049`, часы сдвинуты на +137 дней (машина считает, что
сегодня 29.01.2027):

```
3939 passed, 1 skipped, 1 warning in 18.19s
```

Ни одного падения. Проверки кнопки загрузки отдельно — на +400, +137 и −400 дней:
`52 passed` каждый раз.

~~**Вывод: в сюите нет других сторожей, которые держатся на календаре машины.**~~

⚠️ **Вывод опровергнут в тот же день** (проверка сторожей `B-049` мутацией,
`D-112`). Он снят на **одном** сдвиге, +137 дней, и этого мало. Тем же
инструментом на больших сдвигах:

⚠️ Режим прогона назван у каждой строки: числа последовательного прогона одного
файла и прогона всей сюиты на `-n auto -m "not slow"` **не сравнимы между собой**
(часть падений уносит с собой сбор соседей, часть проверок отфильтрована).
Сравнивать строку можно только со строкой того же режима.

| Сдвиг часов | Красных | Где | Режим |
|---|---|---|---|
| +137 дней | 0 | — | вся сюита, `-n auto` |
| +400 дней | 5 | `tests/test_backtest_main.py` | вся сюита, `-n auto` |
| +800 дней | 5 | `tests/test_backtest_main.py` | вся сюита, `-n auto` |
| **−137 дней** | **28** | `tests/test_app_backfill.py` | вся сюита, `-n auto` |
| −400 дней | 28 | `tests/test_app_backfill.py` | вся сюита, `-n auto` |
| −800 дней | 28 | `tests/test_app_backfill.py` | вся сюита, `-n auto` |
| +300 дней | 0 | — | один файл, последовательно |
| **+310 дней** | **4** | `tests/test_backtest_main.py` | один файл, последовательно |
| +330 дней | 9 | `tests/test_backtest_main.py` | один файл, последовательно |

Верный вывод: `tests/test_ui_history_load.py` протух **первым**, а не единственным.

**День, когда покраснеет следующий, известен точно.** Бисекция по всей сюите
(`-n auto -m "not slow"`), шаг до одного дня:

| Машина считает, что сегодня | Красных |
|---|---|
| 11.07.2027 (+300) | 0 |
| 16.07.2027 (+305) | 0 |
| 19.07.2027 (+308) | 0 |
| **21.07.2027 (+310)** | **3** |
| 23.07.2027 (+312) | 4 |

Запас — **310 дней**. Разбор и что чинить — `D-112`.
Замер на одном значении сдвига отвечает на вопрос «протухло ли уже», а не
на вопрос «держится ли на календаре»: для второго нужны оба направления
и несколько расстояний.

## 4. Когда протух `B-049` — по дням

Тем же инструментом на дереве **до** починки. Отрезок загрузки «последние 7 дней»
уезжает вправо от подставных данных за 03.09.2026:

| Машина считает, что сегодня | Красных из 48 |
|---|---|
| 05.09.2026 | 0 |
| 06.09.2026 | 0 |
| 09.09.2026 | 0 |
| **10.09.2026** | **2** |
| 11.09.2026 | 3 |
| 12.09.2026 | 3 |
| 13.09.2026 | 4 |
| 14.09.2026 | 4 |

Отсюда закрывается вопрос «когда сломалось», стоявший в `B-049`: не ломалось
ничего. Первые две проверки покраснели 10.09.2026, последние — 13.09.2026,
и ни одна строка Python в эти дни не менялась.

Заодно: замер `3979 passed, 0 failed`, записанный в проекте датой 10.09.2026,
снят **не на этом дереве** — 10.09 эти две проверки уже обязаны были краснеть.

## 5. Чем закрыто

`HistoryPort` получил довод `clock` — источник «сейчас», умолчание прежнее
(системные часы в МСК). Проверки задают свой день и строят данные вокруг него.
Два новых сторожа стоят на самой болезни:

* `test_the_button_works_on_any_day_of_the_calendar` — тот же путь в 2024, 2026
  и 2031 году; три дня, а не один, потому что единственный день, случайно совпавший
  с сегодняшним, зеленел бы и на системных часах;
* `test_the_port_takes_its_today_from_the_clock_it_was_given` — правая граница
  запроса, ушедшего на биржу, равна названному дню.

Мутация: возврат `datetime.now(MSK)` в `_load_history` роняет восемь проверок сразу,
а не молчит до наступления срока.

## 6. Что стоит сделать, но не сделано без решения владельца счёта

Прогон сюиты со сдвинутыми часами **раз в неделю на бегунке** — отдельным заданием
с `CLOCK_SHIFT_DAYS=180`. Он ловит протухание за полгода до того, как оно случится,
и стоит двадцать секунд машинного времени. Требует `gcc` на бегунке (есть) и работает
только на Linux — под Windows такой проверки не будет.
