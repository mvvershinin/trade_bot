## 1. Блокирующие

### 🔴-A. §4.2/§4.6 — снимок, пришедший до конца догрузки, исполняет заявку в полёте по `open` текущего бара

🔴-3 первого круга закрыт **в движке** и переоткрыт **в адаптере**.

Сценарий: вход подан на закрытии `[10:15, 10:20)` (`submitted_at = 10:20`), сокет умер
в 10:20:06, переподключение в 10:37:20. Сервер сразу шлёт последнюю известную свечу —
снимок 10:37 через 0,1 с после подтверждения, **до** ответа HTTP-догрузки. `ride()` пишет
минуту, читает `bars(...)`, текущий бар `[10:35, 10:40)` уходит в `on_market_candle`
незакрытым; `runner.py:437` зовёт `_exchange` **до** `intake`, исполнитель получает бар,
`_ready`: `10:35 >= 10:20` → вход исполнен по `open` минуты 10:35. Догрузка приходит
через секунду — заявки в `pending` уже нет.

**Это не гонка:** порядок «подтверждение → последняя свеча → ответ HTTP» детерминирован.

План говорит только «бары, чей интервал пересекает обрыв, не закрываются „по данным“» —
про закрытие, не про подачу незакрытого. Тест §3 х проверяет `Engine.feed` в отрыве
от `ride()`. Мутации «снимок в движок до конца догрузки» в §6 нет.

Цена: на MIX 300–1 000 ₽ на контракт вымышленного результата на каждой заявке,
пережившей обрыв.

**Исправление:** пока идёт догрузка, снимки **только пишутся в базу**; в движок не идёт
ничего — ни закрытый бар, ни незакрытый. Порядок строго «подписка → догрузка
`[…, первая минута потока)` → `feed` закрытых → первый незакрытый в `on_market_candle`».
Тест: поддельный сокет отдаёт снимок 10:37 сразу после подтверждения, поддельный HTTP —
на 500 мс позже; ожидание: единственная сделка `at == 10:20`, сделки с `at == 10:35` нет.

### 🔴-B. §4.4 — правило свежести даёт сделку по цене, которая была ДО решения

Закрытый бар считается свежим, пока не мог закрыться следующий (`server_now < close_time + N`),
и идёт в `on_market_candle`; модель исполняет по `open` первого бара с `time >= submitted_at`.

Сценарий: переподключение в 10:37:20, догружены минуты до 10:36. Бар `[10:30, 10:35)`:
`close_time + N = 10:40 > 10:37:20` → **свежий** → сигнал → заявка `submitted_at = 10:35`.
Следующий `fills_at` — с текущим незакрытым баром `[10:35, 10:40)`, `time = 10:35 >= 10:35`,
цена — его `open`, **на 2 мин 20 с раньше решения**. Вариант «старт»: программа запущена
в 10:23:40, последний закрытый бар `[10:15, 10:20)` свежий по тому же правилу — сделка
по `open` 10:20 при решении в 10:23:40.

Проверка в три строки: `submit(OPEN, LONG, submitted_at=10:35)`;
`fills_at(unsettled bar: time=10:35, open=100.0, close=105.0)` → `Fill.price == 100.0`,
хотя в момент решения цена 105.

Цена: ход за до 5 минут на MIX — 100–500 пунктов, **и знак не случайный**: после
пересечения средней цена чаще идёт в сторону сигнала, значит бумажный вход систематически
**лучше** настоящего. Симуляция, по которой выбирают объём, завышает результат
на каждом переподключении внутри окна — а заказчик: «интернет прерывается часто».

**Исправление** — одно из двух, первое предпочтительнее:
1. свежесть ⇔ `server_now − close_time ≤ G + 5 с`; всё, что обнаружено позже, — `feed`,
   решает следующий бар; в §5 — строка «сигнал бара, закрывшегося за время обрыва,
   пропускается: модель не может исполнить его честно»;
2. модель на незакрытом баре исполняет по `candle.close` — трогает
   `backtest/execution.py`, меняет цену всех живых исполнений.

⚠️ **Ошибка критика первого круга:** правило стояло в редакции 2, следствие с моделью
не было замечено.

## 2. Существенные

**🟡-1. §4.6 — догрузка до `now` перезаписывает минуту, которую уже ведёт поток.**
Ранг равный, «последний записанный побеждает»; если ответ HTTP ложится после снимка
потока за ту же минуту, а он старее (кеш) — минута усечена. Порядок «подписка ↔ догрузка»
не назван. Исправление: догрузка **после** подписки, диапазон
`[минута последней принятой свечи − 1, первая минута потока)`, минуту потока HTTP не трогает.

**🟡-2. §4.1 — `server_now = local_now + offset` читает те же часы, от которых защищается.**
Скачок локальных часов между замерами сдвигает `server_now`; на тихой минуте замера нет
30+ с. Исправление: ход времени — `time.monotonic()`; замер старше 60 с — правило 2
выключено.

**🟡-3. §4.3 — поток брокера умер при живом сокете.** Сокет отвечает на ping, свечи
не идут. Бар закрыт по часам с усечёнными минутами; `Offline` не было, догрузки нет,
счётчик §3 б молчит. Исправление: правило 2 требует ещё свежую котировку
(`securityTradingStatus == 17`, `dateTime` не старше 60 с); после закрытия по часам
с пустыми минутами — один HTTP-запрос этих минут.

**🟡-4. Частота канала котировок не замерена**, а «нагрузка — не риск» утверждается.
Котировки на MIX могут идти десятками в секунду. Замер одной минуты до кода; смещение
считать не чаще раза в секунду.

**🟡-5. Два пути закрытия бара (снимок и таймер) не сериализованы.** Чередование между
`await` даёт двойное закрытие; сегодня спасает фильтр `intake`, на этапе 2 с настоящим
`await fills_at` чередование попадёт внутрь `on_market_candle`. Исправление: `asyncio.Lock`
либо одна очередь.

**🟡-6. §3 ы — сторож «поле без виджета» в записанной форме не пишется:** нужна карта
поле → виджет, имена расходятся (`take_profit_pct` ↔ `dialog.take_profit`), рукописная
карта станет четвёртым перечислением. Исправление: круг `set_values → values()`
с неумолчательным значением; поле, не пережившее круг, обязано быть в явном списке
отложенных.

**🟡-7. `last_message_at` по локальным часам** — при смещении на 90 с перескакивает
минуту обрыва. Считать от `dateTime` снимка (метка сервера).

**🟡-8. Пустая база и инструмент без истории не названы.** `Settings.instrument`
умолчанием `MXU6`, экспирация 17.09.2026 — через две недели умолчание даст `NOT_FOUND`
на подписке и `Backoff` по кругу. Текст отказа: «инструмент не найден или истёк».
