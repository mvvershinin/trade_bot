## 1. 🔴 Правка цикла событий сделана в одном из семи мест, основание для остальных ложно

Отчёт `.docs/tests/test-expert-izolyaciya-2026-09-06-1432.md` §6 понижает 658 тестов
до 🟡 словами «Пока безвредно ровно потому, что цикл событий крутит только
`test_ui_history_load.py` — там теперь стоит защита». `grep` говорит обратное:
`qasync.QEventLoop(qapp)` строится ещё в шести местах, и ни в одном нет
`setQuitOnLastWindowClosed(False)`:

```
tests/test_app_port.py:144
tests/test_app_observe_port.py:69
tests/test_app_runs.py:93
tests/test_app_settings_wiring.py:68
tests/test_ui_backtest.py:88
tests/test_ui_history_load.py:1012   встроенный цикл внутри
                                     test_the_fixture_finishes_the_tasks_a_failed_test_abandoned
```

**Сценарий.** Один из 658 тестов, оставляющих показанное окно (их собственный замер),
достаётся воркеру перед `tests/test_ui_backtest.py::test_a_run_reaches_the_report_with_money_split_three_ways`
→ `DeferredDelete` исполняется внутри `QApplication.exec()` → `lastWindowClosed`
→ `quit()` → `Event loop stopped before Future completed` у невиновного.
Это тот самый дефект, который объявлен закрытым.

**Исправление:** `setQuitOnLastWindowClosed(False)` плюс `_settle_qt` одной общей
фикстурой в `conftest.py`, а не шестью копиями.

## 2. 🔴 `make_dialog` не убирает за собой

Ровно эту связку `tests/test_ui_hover.py:113` и
`tests/test_ui_history_load.py::test_a_bare_process_events_leaves_a_deleted_window_alive`

Докстринг фикстуры (стр. 66-68) утверждает противоположное и выдаёт неработающую
уборку за причину правки.

**Последствие.** `test_tab_order_follows_the_screen` (650),
`test_the_alerts_follow_the_theme` (793),
`test_every_line_of_the_settings_is_readable_in_both_themes` (911)

который «изолировали». В `test_ui_hover.py` на это поставлен сторож
`the_panel_must_not_outlive_the_test`; в `test_ui_settings.py` — ничего.

⚠️ Это не пересказ `D-083`: там про счётчик живых виджетов, здесь — про то,
что заявленная половина новой фикстуры не работает и никем не стережётся.

## 3. 🟡 `SCREEN_ALLOWED` не даёт обещанного, а первая строка в нём кладёт прогон без виноватого

`tests/conftest.py:66,83-84` **безусловно** присваивает `offscreen` и удаляет
`DISPLAY`/`WAYLAND_DISPLAY` из `os.environ` в шапке модуля, до любой фикстуры.
Тест, вписанный в `SCREEN_ALLOWED`, экрана всё равно не получит — возвращать
`DISPLAY` некому, — то есть текст отказа «Нужен настоящий экран, впишите тест
поимённо в SCREEN_ALLOWED» ведёт в тупик.

Хуже второе: `the_run_stays_screenless:440-443` для разрешённого теста пропускает
и **выходную** проверку, поэтому `_poisoned_by` остаётся пустым; если такой тест
всё-таки поднимет Qt на экранной платформе, каждый следующий тест воркера падает
на входной проверке с текстом «кто поганил — не записано». Это ровно тот режим,
который комментарий на стр. 445-449 объявляет отвергнутым.

## 4. 🔴 Храповик `ast` слеп к тому, как виджет построен в его же файле

`test_no_test_here_builds_a_qt_widget_without_asking_for_the_application` считает
нарушителем только `ast.Call` с `call.func` вида `ast.Name` (стр. 1566).
Строка 627 того же файла — `ui.main_window.MainWindow(port=port, sanitize=redact)` —
это `ast.Attribute`; сверх того `MainWindow` не попадает и в `_widget_names`,
потому что `import ui.main_window` — это `ast.Import`, а сканируются только
`ast.ImportFrom` (стр. 1496). Двойной промах.

**Сценарий.** У `test_change_travels_from_window_to_engine` убирают `qapp`
из подписи (или пишут новый тест на `MainWindow`) — храповик зелёный,
`pytest tests/test_ui_settings.py::test_change_travels_from_window_to_engine`
роняет процесс с кодом 134 без единого сообщения. Тот класс отказа,
ради которого храповик и поставлен.

Той же природы: виджет, построенный во вспомогательной функции модуля
(обход идёт только по телу теста), и `ast.AsyncFunctionDef`, не обрабатываемый
ни в `_fixtures_that_bring_the_application`, ни в обходе нарушителей.
