# Создать торговую заявку

URL: https://trade-api.bcs.ru/http/operations/create

```
POST
## https://be.broker.ru/trade-api-bff-operations /api/v1/orders
```

**Работает только при наличии прав для торговли.**

О торговле вне биржи: класс **QMEBLCK** (БКС), класс **MTQR** (МосБиржа).

## Request — Body (application/json), required

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| **`clientOrderId`** | uuid | **да** | **Уникальный идентификатор заявки. Вам нужно сгенерировать самостоятельно в формате UUID. Используется для отслеживания и предотвращения дублирующих заявок** |
| `side` | string | да | `1` Покупка, `2` Продажа |
| `orderType` | string | да | `1` Рыночная · `2` Лимитная · `3` Алгоритмическая GTD · `4` Айсберг · `5` Условная |
| `timeInForce` | string | нет | `1` Day (только в течение торговой сессии) · `2` Fill Or Kill · `3` Good Till Date до `expiryDate`. `1` и `2` — для рыночных и лимитных; `3` — только для алгоритмических. **Default:** `1` |
| `expiryDate` | string | усл. | `YYYYMMDD`, обязательна при `timeInForce = "3"`; не раньше даты подачи и не позже 30 календарных дней |
| `orderQuantity` | int64 | да | Количество в заявке (шт.), `>= 1` |
| `ticker` | string | да | Тикер инструмента, `non-empty` |
| `classCode` | string | да | Код класса ценной бумаги (таблица Boards MOEX ISS; акции обычно `TQBR`) |
| `price` | number | усл. | Цена за одну штуку, > 0, до 8 знаков. Для лимитных, алгоритмических, айсберг и условных. ⚠️ Учитывайте ограничения МосБиржи на уровень цены, иначе заявка будет отклонена биржей |
| `stopPrice` | number | усл. | Стоп-цена условной заявки; обязательна в сценариях со стоп-лоссом |
| `takePrice` | number | усл. | Цена тейк-профита; обязательна в сценариях с тейк-профитом |
| `visible` | integer | усл. | Видимое количество айсберга, < `orderQuantity`, обязательно при `orderType = "4"` |
| `executionTakeProfitType` | integer | нет | `1` рыночное, `2` лимитное |
| `executionStopLossType` | integer | нет | `1` рыночное, `2` лимитное |
| `spread` | number | нет | Защитный спред условной заявки |
| `spreadType` | integer | нет | `0` валюта цены, `1` проценты. **Default:** `0` |
| `offset` | number | нет | Отступ условной заявки |
| `offsetType` | integer | нет | `0` валюта цены, `1` проценты. **Default:** `0` |

```json
{
  "clientOrderId": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "side": "1", "orderType": "1", "timeInForce": "1", "expiryDate": "string",
  "orderQuantity": 0, "ticker": "string", "classCode": "string",
  "price": 0, "stopPrice": 0, "takePrice": 0, "visible": 0,
  "executionTakeProfitType": 1, "executionStopLossType": 1,
  "spread": 0, "spreadType": 0, "offset": 0, "offsetType": 0
}
```

## Responses

**200 OK** — `clientOrderId` uuid, `status` string (**Example:** `OK`)

**400 / 401 / 403 / 404 / 422 / 429 / 500** — общая форма отказа
(`timestamp`, `traceId`, `type`, `errors[]`, `displayOptions`) плюс код `USER_NOT_FOUND`.

Base URL `https://be.broker.ru/trade-api-bff-operations`, Bearer JWT.

## Зачем это нам — ключ от повторной заявки

⚠️ **`clientOrderId` генерируем МЫ, и он «используется для отслеживания
и предотвращения дублирующих заявок».** Формулировка дословная — официальный
PDF `trade-api-docs.pdf`, «Создание торговой заявки», поле обязательное, тип
UUID. Это тот механизм, которого не хватало в разборе обрыва связи: отправили
заявку, связь пропала до ответа, робот не знает — дошла или нет.

⚠️ **Поправка 06.09.2026 (`B-002`).** Здесь стояло: «Повтор с тем же
`clientOrderId` не создаёт вторую заявку». **В документации этого нет.**
Названо только назначение поля; что сервер делает при повторе с тем же
ключом — не описано нигде: ни кода отказа, ни срока, ни области уникальности.
Слово «дублирующих» встречается в PDF ровно один раз, в строке этого поля.
Живьём не проверялось (токена в разработке нет). Поэтому автоматический
повтор подачи на этом утверждении **не строится**: пишущий запрос слой
не повторяет вовсе (`broker/session.py`, таблица `REPEATABLE`), а после
потери ответа судьба заявки выясняется запросом статуса по тому же ключу.

Следствия, которые надо записать в контракт боевого исполнителя:

⬜ `clientOrderId` **записывается до отправки** и переживает потерю ответа:
   спрашивать статус не о чем, если ключ потерян вместе с ответом. Повтор
   подачи с тем же ключом «на авось» запрещён, пока поведение сервера
   не проверено живьём;
⬜ он же — естественный ключ связи «наше решение ↔ заявка у брокера»
   и вход для `11-get-order-by-id.md` (`orderIdType = 1`);
⬜ **200 OK означает «заявка принята», а не «сделка совершена».** Факт исполнения
   приходит отдельно — потоком статусов (`24-ws-order-status.md`) с `executionId`
   и `commission`. Путать эти два события нельзя: журнал сделок заполняется
   по второму, а не по первому.

⚠️ **Работает только на токене с правами торговли.** Сегодня в `userdata/` лежит
токен `trade-api-read`. Предохранитель «боевой режим не включается на токене
только для чтения» обязан ловить это **до** нажатия «Старт», а не отказом 403
в момент подачи заявки.

⚠️ Лимит: 10 RPS и **200 000 заявок в сутки** (`29-restrictions.md`).
