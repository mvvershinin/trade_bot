### 1. 🟠 Medium — ответ биржи переписывает файл настроек владельца без человека (пункт г)

**[app/main.py:966-977 `_keep_settings.remember`] + [app/port.py `_point_taken` → `apply_settings(by_person=False)`, `_step_taken` → `self._file_holds.pop("price_step")`]**

Проба: файл владельца той же формы, что в `test_owner_file_without_step._owner_file`
(шаг 0, пяти ключей `time_exit_*`/`minute_*` нет), порт собран как в `app/main.py`,
затем `attach_exchange(exchange(25.0))` + `refresh`. Окно настроек не открывалось,
«Применить» никто не нажимал. Файл после этого изменился:

```
price_step:             0.0 → 25.0
ruble_per_point_source: ''  → 'биржей — карточка MXU6 (RFUD): шаг цены 25'
time_exit_order:        нет → 'limit'
time_exit_limit_steps:  нет → 10
time_exit_wait_bars:    нет → 1
minute_order:           нет → 'near_first'
minute_bar_limit:       нет → 5
```

Это ровно та находка 04.10.2026, от которой сторож `test_opening_the_settings_does_not_rewrite_the_owner_file`
(дописывание пяти ключей без «ОК»): тот стережёт только открытие окна настроек,
а путь «пришла карточка биржи» не стережётся ничем.

Корень старый: `remember` пишет на каждое эхо `settings_applied`, которое отличается
от прочитанного, и эхо от `apply_settings(by_person=False)` не отличает от человеческого.
Стоимость пункта от биржи шла тем же путём и до этой правки. Новое здесь вот что:
шаг цены теперь меняется на каждом запуске (0 → биржевой), а `_step_taken` прямо снимает
придержку `price_step` с комментарием «в файл идёт биржевой». Так программа сама
переписывает файл при первом ответе биржи у каждого владельца со старым файлом.
Это расходится с докстрингом `for_file`, где «ответ биржи о стоимости пункта (`_point_taken`)»
назван путём, который файл переписывать **не должен**.

Цена в рублях: прямо — 0 ₽. Шаг из файла при запуске обнуляется (`_startup_settings`),
так что записанные 25 на сделки не влияют. Косвенно ломается обещание B-050
«файл не трогается, пока человек не нажал „Применить“»: владелец, сравнивающий свой
файл с тем, что положил, получает в нём ключи и значения, которых не писал.

Что требуется: эхо, вызванное программой (`by_person=False`), в файл не пишется,
либо пишутся только поля, которые программа законно ведёт сама, и это решение
записано. Нужен сторож на этот путь: «карточка пришла → байты файла те же».
Мутация для него — вернуть запись в `remember` на эхо программы.

### 2. 🟡 Low — шаг `NaN`/`inf` от биржи запоминается

**[app/port.py `_learn_step`: `if step <= 0 or ...`] и [market/iss.py:741 `if step is None or step <= 0`]**

`NaN <= 0` даёт False, поэтому `NaN` проходит обе проверки. `json.loads` принимает
литералы `NaN`/`Infinity`, а `float("nan")` — строку. Проба с `exchange(float("nan"))`:
`_point.steps == {'MXU6': nan}`, `values.price_step == 0.0`, движок — `MARKET`.
Направление безопасное: движок отвергает неконечный шаг (`engine/settings.py` `_check_time_exit`),
и выход остаётся по рынку. Но `nan != nan`, поэтому `_learn_step` на каждом ответе
считает шаг новым, `_point_taken` раз в `POINT_VALUE_GAP` гонит `apply_settings`
с отказом, и в журнале повторяется одна и та же строка. В склейке `replace(settings, price_step=nan)`
даст отказ внутри `replay` (не проверял, чем он кончится для прогона). От ISS
такой ответ маловероятен. Что требуется: `math.isfinite(step) and step > 0` в обоих местах.

### 4. ⚪ Info — `can_trade` по `azp` до обмена; поддельный `azp` (пункт б)

**[broker/tokens.py `issued_for`, broker/token_store.py `_settle_scope`, broker/session.py:422-444, :503]**

* Обойти предохранитель подделкой не выйдет. Токен для чтения с вписанным `azp=trade-api-write`
  уходит на обмен с `client_id=trade-api-write` (`session.py:503`). Подпись проверяет брокер,
  получаем `invalid_grant` → `TokenRefused`, рабочего токена нет, заявку подать нечем.
  Чтобы подделать, нужна запись в файл токена, а с ней атакующему проще положить свой токен.
* `can_trade()` возвращает True по непроверенному `azp` **до** успешного обмена.
  Сегодня это ни на что не влияет: `require_trade_rights` в продуктовом коде не вызывается,
  пути подачи заявки к брокеру нет (`app/observe.py` — наблюдение).
  **Требование к будущей проводке боевого режима:** кнопку включать только после
  успешного обмена именно с `client_id=trade-api-write`. Тогда предохранитель опирается
  на то, что подтвердил брокер, а не на нагрузку без подписи.
* Смысловая перемена, о которой владелец должен знать. Раньше пометка «только для чтения»
  в файле на торговом токене действовала как самозапрет: обмен падал. Теперь программа
  считает такой токен торговым и говорит об этом строкой `WARNING` «Тип токена»
  (`live_feed.py:2152`). Молчания нет, и правило 13 соблюдено. Если владельцу нужен
  самозапрет, его надо делать отдельной настройкой, а не типом токена.
* Правило 7: `issued_for` разобранную нагрузку наружу не отдаёт. Исключения гасятся без `as`,
  в журнал попадает только `azp` через `printable_client` (≤ 40 безопасных знаков).
  `scope_notice` содержит только человеческие подписи типов.
