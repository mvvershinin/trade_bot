# Окно «Отчёты», шаг 2: сделки симуляции из базы (Н5)

> Редакция data-expert после гейта и ответов владельца (11.10.2026). Гейт (`architecture-validator`, `code-critic`): устройство годно, слои и правило 1 целы; четыре блокирующие правки вплетены в «Устройство». Фазы: 1 — запись (`market/`, `app/observe.py`); 2 — отбор и окно; 3 — приёмка.

**Чья боль.** Владелец счёта не может открыть сделку симуляции после перезапуска или «Применить»: живой ход пишет в базу только строку прогона (`D-027`), сделки, заявки и решения живут в памяти окна.

**Факт, меняющий постановку.** Прогон симуляции пересчитывает не «день с утра», а весь показанный отрезок: от рубежа контракта плюс прогрев либо от начала глубины показа (`app/port.py::_candles`). Замер на копии базы владельца с умолчаниями: MXZ6 от 16.09 — 4 297 баров, 72 сделки, 385 строк решений, 507 заявок; MXU6 за контракт — 84 дня, 240 сделок, 1 284 строки, 1 469 заявок. По В1 хранится всё пересчитанное.

## Устройство

1. **База: две таблицы, схема остаётся 7.** `CREATE TABLE IF NOT EXISTS`, без пересборки; `journal_session`, `journal_trade`, `journal_decision` не меняются. Номер не поднимается по правилу `market/storage.py:187`: смысл записанного не меняется, а 0.2.4 на такой базе не теряет ни предохранителя, ни строки — новых таблиц она просто не читает, и откат на 0.2.4 цел без копии `userdata/`.
   - `journal_order` — заявки прогона: `session_id`, `order_id`, `at` (момент решения), `kind` (`submitted` | `level_hit`), `action`, `side`, `volume`, `reason`, `exit_reason` (машинное значение), `target_id`, `close_price` и `average` (закрытие и средняя бара, на разборе которого заявка родилась), `level` (уровень тейка, неподвижного или скользящего), `limit_price` (предел выхода по времени) — В4; `phase` (`recount` | `catch_up` | `live`, §2). Пустая ячейка — числа нет. Уникального ключа на имя заявки нет: вооружение повторяется каждый бар под тем же именем.
   - **Миграция колонки `phase`** (12.10.2026, таблица уже стоит в базе владельца, строк 0): при каждом открытии, если колонки нет по `PRAGMA table_info`, — `ALTER TABLE journal_order ADD COLUMN phase TEXT NOT NULL DEFAULT 'recount' CHECK (…)`. Определение колонки одно на `CREATE TABLE` и `ALTER` (`_ORDER_PHASE_COLUMN`). Номер схемы не поднимается, пересборки нет; строки отладочных сборок получают `recount` — безопасную сторону.
   - `journal_run_rows` — отметка «строки прогона записаны»: `session_id` (PK), `kept_since` (начало первого бара пересчёта, В1), `live_from` (закрытие последнего бара первого прохода — **сведение, а не граница живого**: колонка уже в базах, снимать её — переезд таблицы без выигрыша). Обе пусты — в первом проходе движку не дали ни одного бара. Нет отметки — строк нет (так у 35 прежних прогонов).
   - Сторожа в `_GUARDS` по образцу журнала, одной таблицей на четыре таблицы строк: только дописывание, строки умирают с прогоном, вставка только в открытый прогон. Текстовые колонки `journal_order` чистятся `_clean` по `_ORDER_TEXT_COLUMNS`, тест сверяет список с `PRAGMA table_info`; токен ищется и в байтах файла (0011 п. 9).
   - `write_paper_rows` — одна транзакция: отметка, решения, заявки, сделки. Сделки отсеиваются по `_TRADE_IDENTITY` внутри `market/`; ответ — сколько записано и сколько отсеяно. Строки без отметки и строки прогона по истории отвергаются (опора `RUNS_KEPT`).
   - Заявки читаются только с номером прогона, `origin` в строке обязателен (0011 п. 4); прогоны `PAPER` — по кодам инструмента вместе с отметкой. `journal_stats` считает и новые таблицы.
2. **Кто пишет — `LiveObserver` (`app/observe.py`)**, в конце каждого `feed`, в той же корутине (решение 0033).
   - `ShadowExecutor.submit` запоминает `OrderRequest`; `_walk` добавляет закрытие бара и среднюю; касания — из `level_plans`. Списков три (журнал, заявки с касаниями, сделки) плюс признак отметки, у каждого свой курсор.
   - **Одна запись в полёте.** Отменённый `await` не отменяет работу в потоке базы (`market/worker.py:327`), а проход и закрытие хода — разные задачи (`app/port.py:2895-2901`, `:3515`). Поэтому замок записи; пачка уходит задачей и ждётся через `shield`; следующий писатель сперва дожидается записи в полёте. Курсоры сдвигаются в потоке базы сразу после фиксации (образец — `_open_store`, `market/worker.py:324-334`): успех не теряется при отмене ожидающего. `_walk` останавливается по `_stopped`.
   - **Фаза у каждой строки заявки** ставится в `_walk` при разборе бара — по тому, как бар пришёл, а не по времени (правило 1: движок о фазе не знает). `recount` — бары первого прохода, давшего движку хоть один бар и дошедшего до конца; `catch_up` — в следующих проходах все бары пачки, кроме последнего; `live` — последний бар пачки. Отмена посреди прохода оставляет разобранным барам их фазу и пересчёт не кончает. Названный край: два бара в одном проходе дают старшему `catch_up` (решён с опозданием на бар) — осознанно, выдать догон за живое дороже.
   - **Отметка пишется на первом `feed` всегда**, даже без строк: «ноль сделок» отличим от «не записывали».
   - **`aclose`**: остановить ход, дождаться записи в полёте, дописать остаток, потом закрыть прогон.
   - `RunEntry.id is None` — ничего не пишется; для `PAPER` свой текст отказа открыть прогон («Симуляция не записывается», `app/runs.py:578`).
   - Отказ записи (правило 13): одна WARNING на серию («Сделки симуляции не записаны в базу: <причина>»), при восстановлении — «Запись симуляции восстановлена: дописано N»; отказ в `aclose` — ERROR «потеряно N сделок, M строк», то же в `log.error` (окно уже закрыто, `app/main.py:788-793`) и в `finish_note`. В остановку робота отказ не попадает (`app/port.py:3583`, `run.halted`).
3. **Связь сделки с заявками и решениями.** Заявки — по `(session_id, entry_order_id | exit_order_id)`; заявкой выхода считается последняя строка с этим именем не позже выхода. Причина входа — `reason` заявки входа, выхода — `exit_reason` сделки и `reason` заявки выхода; уровень — `level` строки `level_hit` либо `limit_price` заявки выхода. Строки решений — по `(session_id, at)`: все строки этого бара. Снимок настроек — `journal_session.settings`. `engine/`, `backtest/`, `strategies/` не правятся.
4. **«Как было» и «пересчёт с утра»** (фаза 2) — только отбор строк в `app/paper_report.py`, движок один (правило 1). Инструмент — тот, что на экране, все его контракты одним рядом (В3).
   - **«Как было»** — сделки, у которых строка решения выхода (заявка выхода либо `level_hit`) в фазе `live`. Вход `recount` — пометка «вход из пересчёта» (В2), `catch_up` — «вход на догоне». Ответ владельца 12.10: вход `live` при выходе `catch_up` — строка «выход на догоне» и в итоге; выход `catch_up` без живого входа — числом над таблицей («Сделок, решённых на догоне (…): N», не в итоге); разбиение по фазе сделки — `_AS_WAS` в `app/paper_report.py`. Граница во времени (`live_from`) отвергнута находкой `/review`: догрузка выходных одной пачкой и пустой первый проход объявляли пересчёт живым. Строки решения нет — `recount`.
   - **«Пересчёт с утра»** для дня D (МСК) — сделки с выходом в D у последнего прогона, **шедшего в D**: `started_at` ≤ конец D и конец прогона ≥ начало D; конец — `finished_at`, у аварийного прогона без него — наибольший `at` его строк (нет строк — `started_at`). Последний — по `started_at`, равные — по `id`. Не шёл никто — «прогона нет».
   - Дни до старта прогона (В1) хранятся свидетельством и полной связкой заявок для «входа из пересчёта»; правило «пересчёта» их не берёт.
   - Прогон без отметки не выдаётся за «0 сделок»: «N прогонов симуляции за период: сделки не записывались».
5. **Окно** (фаза 2). Переключатель над таблицей: «Прогон на экране» (при открытии, В5) / «Симуляция: как было» / «Симуляция: пересчёт с утра». Запрос — команда и сигнал в `ui/ports.py`; порт читает через `MarketWorker`, перекладывает в `app/convert.py`; в окно — `TradeRow` и разбор `TradeStory` (новый `ui/trade_story.py`). Разбор = `trade_lines` шага 1 + `story_lines(TradeStory)`, одна функция для базы и для памяти. `ui/models.py` не меняется.
6. **`RUNS_KEPT = 200` остаётся**: проход по истории строк не пишет. Сторож `tests/test_app_runs.py` переименовывается («проход по истории строк не пишет», и по новым таблицам), рядом — «прогон симуляции строки пишет». Строки симуляции не удаляются: прогон `PAPER` — свидетельство.

## Что сломается → чем поймано (сторожа ставит и ломает мутацией test-expert)

- Сделка не переживает перезапуск → «падение» без `aclose` и новое открытие базы. Мутация: писать только в `aclose`.
- Остаток теряется при закрытии → в `aclose` запись раньше закрытия прогона. Мутация: порядок.
- Дубли → два сброса подряд, повтор после отказа, отмена прохода посреди записи и `aclose` следом. Мутации: курсор не сдвигается, сдвигается до записи, `aclose` не ждёт записи в полёте.
- Отказ записи молчит → подставной `MarketWorker`: одна WARNING на серию, строка о восстановлении, ERROR и `log.error` на `aclose`. Мутация молчания.
- Отказ записи останавливает робота → `run.halted` пуст при отказах.
- Граница по часам машины → отметка равна закрытию последнего бара первого прохода и пишется без строк.
- Догон, пустой первый проход или отмена первого прохода объявлены живыми → `tests/test_app_paper_phase.py` (фазы строк по проходам, «как было» по устройству ленты).
- Колонка фазы не доехала до базы владельца → таблица без неё: после открытия колонка есть, строка цела с `recount`, `CHECK` отвергает чужое, `replaced_guards` пуст.
- «Как было» показывает пересчитанное; «пересчёт» берёт не тот прогон; UTC и МСК; разбор из базы расходится с разбором из памяти; старый прогон без строк выглядит пустым → тесты фазы 2.
- Миграция теряет журнал → база схемы 7 со строками: после открытия строки целы, `replaced_guards` пуст.
- Новая текстовая колонка не чистится → `PRAGMA table_info(journal_order)` и байты файла.
- Сторожа ослаблены → `UPDATE`, прямой `DELETE`, вставка в закрытый прогон отвергаются.
- Проход по истории начал писать строки → сторож `tests/test_app_runs.py` по четырём таблицам.

## Что не закрывает

- Строка решения привязана к заявке по моменту бара, а не по имени; точная привязка — `JournalEntry.order_id`, правка `engine/`, отдельный гейт.
- Позиция, открытая в момент «Применить», сделкой не становится ни в одном прогоне.
- Опоздавший бар попадает в «как было»; об опоздании говорит строка «Свеча пришла поздно».
- «Применить» без изменения торговых настроек нового прогона не открывает (`D-033`).
- У 35 прогонов симуляции до этой сборки строк не будет. Кнопки удаления строк симуляции нет.
