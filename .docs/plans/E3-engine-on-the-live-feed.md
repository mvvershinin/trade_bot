# Миниплан: Э3 — движок на живом потоке, режим наблюдения

Поставлено 05.09.2026. Этап `ROADMAP.md` §Э3. Гейт пройден до кода.

---

## 1. Что это делает и чья это боль

Сегодня движок **переигрывает базу**: живая минута записана — и по всей истории
заново гоняется `backtest.replay`. Состояние движка при этом выбрасывается
и выводится заново на каждом баре. Владелец счёта сказал прямо: «движок, которым
пока нельзя пользоваться».

Нужно: **один непрерывный ход движка** — прогрев из базы, затем живые бары тем же
рядом, — который показывает решения в реальном времени. Заявки не подаются.

Это последний этап, где ошибка ничего не стоит, и первый, на котором видно,
ведёт ли себя стратегия в бою так же, как на истории.

## 2. Что здесь способно сломаться — списком, до выбора решения

| # | Что | Цена |
|---|---|---|
| а | Прогрев не подан или подан с другой границы | Средняя другая ⇒ **другой список сделок целиком** (`PROTOTYPE.md` §3). Молча |
| б | Бар отдан движку дважды | Средняя считает его дважды, на пустом снимке — **вторая заявка на вход** |
| в | Бар отдан движку с временем **назад** | Торговый модуль бросает исключение, живой ход умирает посреди дня |
| г | Бар пропущен молча | Дыра в средней. `DOMAIN.md`: «тихой потери свечи не бывает» |
| д | Бар, отброшенный как неполный, стал доверенным **после** того, как робот ушёл вперёд | Свеча потеряна навсегда, и это невидно |
| е | Содержимое уже отданного бара изменила догрузка | Решение принято по неполным данным, и об этом никто не знает |
| ж | Заявка ушла брокеру | Деньги. Этап называется «наблюдение» |
| з | Живой ход и прогон по истории на одних данных дают **разное** | Ровно то, ради чего этап существует; расхождение обязано быть видно |
| и | Настройки сменили посреди ряда | Ход, который не соответствует ни старым настройкам, ни новым |
| к | Прогрев короче, чем нужно средней | Решения по средней, которая ещё зависит от начала ряда |
| л | Строки журнала живого хода неотличимы от прогона по истории | Выгрузка за день читается как боевая или наоборот (решение 0011) |
| м | Запись прогона в базу — по строке на каждый бар | `--runs` заливается 12 записями в час об одном и том же ходе |

## 3. Чем каждое обнаруживается

| # | Обнаружение |
|---|---|
| а | Тест: живой ход и `replay` на одном ряде дают **равные** `HistoryRun` поле в поле |
| б | Тест: повтор всего ряда после прогрева не добавляет ни одной сделки и ни одного бара |
| в | Тест: `LiveSource.offer` не отдаёт бар с `time <= last`; мутация «отдать» — падает |
| г | Отчёт `Seam.gaps` → строка журнала на каждый разрыв в живой фазе |
| д | `Seam.late` → строка журнала WARNING с перечислением времён |
| е | `Seam.changed` (отпечаток `close` + `filled_minutes`) → строка журнала WARNING |
| ж | Тест: исполнитель живого хода — потомок модели исполнения, `broker` в модуль не импортирован; отдельный тест проходит по импортам модуля |
| з | Тот же тест, что «а». Это и есть приёмка этапа без живого рынка |
| и | Наблюдатель пересобирается целиком при смене инструмента, размера свечи, настроек движка или модуля; тест на ключ пересборки |
| к | Строка журнала WARNING, если баров прогрева меньше `market.warmup_bars` |
| л | `RunOrigin.PAPER` («симуляция на боевом потоке») на всех строках живого хода |
| м | Одна запись `RunLog.around` на весь ход, а не на проход |

**Дописано по ходу работы (05.09.2026).** Пункт, которого в списке не было
и который стоил больше всех остальных вместе: **фоновая задача разбора роняла
прогон проверок в SIGSEGV**, причём падало в чужом файле и с плавающим местом.
Обнаружено не тестом, а полным прогоном; найдено выбрасыванием по одному тесту
за пятнадцать прогонов. Лечение — разбор в вызывающей корутине
(решение 0033, раздел «Почему разбор без фоновой задачи»). В графу «чем будет
обнаружено» это не попало бы ни при каком старании: пункта «асинхронная
машинерия» в списке рисков не было вовсе.

## 4. Чего решение НЕ закрывает

* **Живого рынка нет.** Токен в разработке не участвует. Приёмка этапа —
  глазами владельца счёта на живом потоке, и иначе её не сделать.
* **Незакрытый бар движку не показывается** (решение 0033). Значит тейк
  в наблюдении срабатывает на закрытии бара, а не внутри него, — как в прогоне
  по истории. С боевым исполнителем (Э4) это изменится, потому что о сделке
  сообщит брокер.
* **Изменение бара глубже окна сверки** (`RECHECK_BARS`) не обнаруживается.
  Догрузка вчерашней дыры пройдёт молча.
* **Сверки позиции с брокером нет** — вопрос №4, этап 2.
* **Предохранителей нет** (потолок объёма, дневной лимит, ГО) — их пишет
  другой исполнитель, параллельно.

## 5. Чем и на чём проверяется

```
.venv/bin/pytest tests/test_app_observe.py -q
.venv/bin/pytest -m "not slow" -q
.venv/bin/ruff check app market tests
.venv/bin/mypy
```

База — синтетический ряд `tests/synthetic.py` и эталонный ряд сверки
(`tests/test_engine_reference_parity.py` берёт его из `reference/`).
Мутации перечислены в §3 и прогоняются руками со сносом `__pycache__`.
