# Э5 — жёсткое закрытие по концу окна с предельной ценой

Основание: [решение 0060 §3](../decisions/0060-customer-answers-on-the-second-algorithm-settings.md),
вопрос 26 ([`OPEN-QUESTIONS.md`](../OPEN-QUESTIONS.md), п. 4 списка). Статус: миниплан, кода нет.

## 1. Доводка `close_on_time_end`, а не второй механизм

Выход по концу окна уже есть: шаг 6 (`PROTOTYPE.md` §2) на первой свече вне окна подаёт
рыночный `CLOSE` через `_exit`, исполнение — по `open` следующей свечи. Момент, пропуск
позиции «закрывается», снятие тейка до выхода — без изменений. «Жёсткое» добавляет три вещи:

1. **Не выключается у алгоритма №2.** Модуль объявляет требование в реестре
   (`strategies/registry.py`), `app/convert.py` ставит `close_on_time_end=True`, галочка
   в окне выключена с подписью «так требует алгоритм». Движок номера алгоритма не узнаёт.
   **Уточнение 04.10:** `SettingsDemand` (`strategies/registry.py` ~:113) понимает только
   перечисления, а `close_on_time_end` — bool. Требуется только `time_exit_order=LIMIT`,
   и LIMIT сам значит «закрывать по концу окна всегда»; механизм на bool не расширяется
   (задел бы требование «переворот в одной свече» алгоритма №2). Это Ф3.
2. **Форма заявки** — настройка `time_exit_order`: `MARKET` (умолчание; алгоритм №1 —
   нынешний путь байт в байт) / `LIMIT` (у алгоритма №2 принудительно, как п. 1).
3. **Правило на неисполнение** (§4).

Выход перед нерабочим днём (`farewell`) идёт через тот же `_exit` и получает ту же форму:
оба выхода «по времени», разная форма была бы необъяснима человеку.

## 2. Предел считает движок, не адаптер (правило 1)

`предел = close сигнальной свечи ∓ N × шаг цены`, округление к сетке шага **от рынка**
(продажа закрытия лонга — вниз, покупка закрытия шорта — вверх). `bar.close` движок уже
читает на шаге 5 — граница 0008 не задета.

* Новое поле заявки `OrderRequest.limit_price`, своя строка в `FIELD_RULES`: только `CLOSE`,
  необязательно. `price` не переиспользуется — оно значит «уровень тейка».
* Новое `EngineSettings.price_step` — константа инструмента (правило 16 допускает).
  **Решение владельца 04.10:** источник один — общее поле окна `price_step` (`ui/models.py`,
  умолчание `0.0`), оно же у издержек тестера; второго места для числа нет, в движок идёт
  через `app/convert.py`. `app/port.py` сейчас подставляет из карточки только
  `ruble_per_point` (~:3109); подстановка шага туда же — Ф3. `LIMIT` при шаге ≤ 0 — громкий отказ:
  «шаг цены неизвестен, предел не посчитать — дождитесь карточки инструмента или впишите
  шаг», по образцу `slippage_steps > 0 and price_step <= 0` в `app/convert.py`.
* Единица отступа — **только шаги цены** (решение 04.10; вопрос 26 открыт, 10 шагов
  временно). Процент и биржевая планка не делаются.
* ⚠️ **Тихий отказ, названный заранее:** исполнитель, не читающий `limit_price`, делает
  из лимитной рыночную, и ни один нынешний тест не краснеет. Первая мутация.

## 3. Исполнение

**Тестер** (`backtest/execution.py`, отложенные заявки; `_level_fills` не трогается):
при `time >= submitted_at` — `open` не хуже предела → сделка по `open` (проскальзывание
не хуже предела); иначе касание предела внутри бара → сделка по пределу **следующим кругом**,
не в круге исполнений по открытию (контракт `fills_at`); иначе ждёт.
⚠️ Касание лимита ищут **два** пути: `_market_fills` (~:837) и обход минуток
`_walked`/`_fire` (~:784, ~:904). `_fire` перебирает только `self.armed` — лимит в `pending`
обходом минуток не проверится; завести его в `_fire` наравне со сторожем с проверкой
`_reachable` (~:976). Это Ф2 (`backtest-methodologist`). Число исполнений
«не по открытию» — в отчёт, как `LevelGaps`. `ShadowExecutor` наследует модель без правки.

**Бой.** Боевого исполнителя заявок нет (только история и тень) — пишется контракт для Э4
в докстринге порта: `orderType "2"`, `price` на сетке, `timeInForce "1"`, `clientOrderId`;
отказ биржи по планке цены → `ExecutionRefused` → путь `exit_blocked_bars`; частичное
исполнение — не обрабатывается, названо для Э4. `broker/` без кода. Поля сверены по снимку
`.docs/broker-api/13-create-order.md`: сайт отдал только меню.

## 4. Не исполнилась за N свечей

Свечи, не секунды: у движка нет часов, секунды жили бы только в боевом адаптере и развели
бы тестер с боем. Счётчик один — `closing_bars`; порог лимитного выхода — новое
`time_exit_wait_bars` (умолчание 1, граница `MAX_CLOSE_WAIT_BARS`), рыночного — прежний
`close_wait_bars`. Действие — настройка `time_exit_unfilled`:

* **А — умолчание: остановиться, заявку оставить, позвать человека.** Позиция может пережить
  окно; заявка продолжает закрывать при возврате цены; обратной позиции робот не создаёт
  ни в одной ветке. Журнал называет заявку и предел и требует снять её **до** закрытия
  руками — иначе обратную позицию откроет рука человека.
* **Режим «Выключен»:** шаг 1 выходит раньше шага 5 (`engine/pipeline.py` ~:540),
  лимитная заявка живёт и может исполниться. Журнал называет оставшуюся заявку
  **с предельной ценой**; мутация — в §5.
* **Б — отложен владельцем 04.10, не делается.** Снять, дождаться подтверждения снятия, подать рыночную («по любой цене»). Нужна
  отмена заявки закрытия: обобщение `CANCEL_TAKE_PROFIT` с тем же контрактом («возврат =
  заявки нет», `ALREADY_TRIGGERED`, `NO_SUCH_ORDER`). Правка порта — отдельным шагом.
* Отвергнуты: переподача с новым пределом M раз (погоня, M окон без заявки, частичные
  исполнения); молчаливое ожидание до конца сессии (правило 13).

В тестере остановка кончает прогон; строка в отчёте и подборе — «остановлен: закрытие
по концу окна не исполнилось», не выбрасывается.

## 5. Поля (правило 16) и приёмка

⚠️ `time_exit_unfilled` не заводится, пока Б отложен: перечисление с одним
значением — настройка без выбора; поведение А зашито (Ф1, 04.10).
Четыре поля — `time_exit_order`, `time_exit_limit_steps` (временно **10 шагов**, строка
к вопросу 26), `time_exit_wait_bars`, `time_exit_unfilled`: поле и подпись
(`ui/settings_dialog.py`, «Торговое окно»), умолчание (`ui/models.py`), проверка строками
таблицы (`engine/settings.py`), журнал (`_CHANGE_ROWS`), снимок прогона (`app/runs.py`,
`app/convert.py`), файл настроек (`app/settings_store.py`: нет полей → умолчания вслух).

* **Сверка 127/127 при прежних настройках** (алгоритм №1, `MARKET`) — после каждого шага
  в `engine/`. С `LIMIT` сверка не обещается.
* **`/risk`**: знак и сторона предела; округление от рынка; одна живая заявка на выход;
  при Б рыночная только после подтверждённого снятия; отказ планки не зацикливается молча;
  у алгоритма №1 умолчание `MARKET` не изменилось.
* **Мутации (`test-expert`)**: знак предела перевёрнут; `limit_price` игнорируется;
  касание отдано в круге открытия; алгоритм №2 слушается снятой галочки; Б без
  подтверждённого снятия; порог взят от рыночного выхода; шаг 0 при `LIMIT` проходит молча;
  строка «Выключен» не называет предельную цену оставшейся заявки.

## 6. Порядок и роли

`strategy-quant` (settings, contracts, шаг 6 и ветка «закрывается» `_rearm_take_profit`;
сверка) → `backtest-methodologist` (модель в `execution.py`, счётчик в отчёте; сверка) →
`desktop-ui-expert` (реестр, `app/`, окно) → вариант Б после `/risk` на первые три →
`test-expert`, `/risk`, `/parity`.

⚠️ **Пересечение с параллельной работой** (скользящий уровень внутри свечи; автопереход
на контракт): `engine/pipeline.py` — `_rearm_take_profit` правят обе; `backtest/execution.py` —
здесь отложенные заявки, там `_level_fills`; `app/port.py` — здесь подстановка шага рядом
с `ruble_per_point`. Условие «после слияния параллельной» снято: З9 слита в 245cc72. `app/live_feed.py`
не трогается.
