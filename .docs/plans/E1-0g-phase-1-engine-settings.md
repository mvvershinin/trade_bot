### Слепые клетки матрицы: почему нужны два базовых ряда

Найдено третьим кругом гейта (test-expert), подтверждено прогоном:

```
на умолчаниях:  trailing_offset_percent=-5.0 → ПРОШЛО
                trailing_step_percent=-5.0   → ПРОШЛО
с трейлингом:   оба отказывают, как должны
nan:            ловится всегда — тот цикл не огорожен
теста на эти два отказа:  ни одного
```

Причина: обе проверки живут внутри `if self.trailing_take_profit:`, а поле по умолчанию
`False`. Матрица «одно поле варьируем, остальные умолчания» их **не задевает** —
и осталась бы зелёной до и после того, как шаг 3 сотрёт любую из двух.

Отягчающее: на эти два отказа **нет ни одного теста сегодня**. Тест
`test_engine_take_profit.py:1980` покрывает пару `trailing_start` против
`trailing_offset`, но не знак самого отступа и не знак шага.

**Следствие для матрицы: два базовых ряда.** Первый — умолчания. Второй —
`trailing_take_profit=True`, и по нему гоняются три поля трейлинга. Без второго ряда
шесть клеток (3 поля × {0, отрицательное}) структурно недостижимы.

⚠️ Строка §3(д) «покрывается матрицей из (г)» в редакции 3 была **неверна** для этих
двух правил. Исправлено здесь.

### Форма матрицы: 136 клеток — раздутие

Осмысленно различных исходов меньше, чем клеток:

* у четырёх перечислений (`mode`, `window`, `reversal`, `partial_candles`) — **два**:
  верный тип и чужой. `nan`, `inf`, 0, отрицательное дают одну и ту же ветку;
* у пяти булевых — около трёх: верный, чужой тип, `0`/`1` целым числом;
* полный разброс нужен только **восьми числовым** полям.

Итого около 85–90 содержательных клеток против 136, без потери ни одной находки
мутаций 3 и 4. Лишний сторож стоит не меньше отсутствующего: его правят при каждом
изменении и однажды правят неверно.

### Почему тест через `dataclasses.replace` этот дефект не увидит

Замерено 03.09.2026, второй круг гейта:

```
настройки не менялись, объём равен:     1.0 == 1.0
нынешний код (!=):                       изменение не видно — верно
таблица на тождестве (is not):           изменение ВИДНО — ложная строка
в журнал ушло бы:                        «Объём: 1 → 1»
```

Причина: `app/convert.py:277` собирает `volume=float(values.volume)` — **новый объект
при каждом вызове**, и в бою настройки идут именно этим путём (`app/port.py:258`).
А `dataclasses.replace`, на котором стоит и нынешний тест, и предложенный в §3(а)
достроенный список, передаёт нетронутым полям **тот же самый объект** — на такой паре
тождество неотличимо от равенства.

То есть прогон остался бы зелёным, а владелец счёта увидел бы в журнале-свидетельстве
строку об изменении, которого не было. Для журнала выдуманная строка не лучше
пропущенной.

⚠️ Проверено только `volume`: у остальных числовых полей объект на обоих путях
совпадает. Дефект узкий, но он ровно в том поле, которым считаются деньги.

## 4. Порядок работ

1. **Заморозочная матрица (г), достройка списка (а) И тест на паре из `app/convert` (з).**
   Все три — до единой правки кода. Обязаны быть зелёными на нынешнем коде, иначе
   описывают не то, что есть.
   ⚠️ Тест (з) назван здесь **явно**, потому что в редакции 3 он в шаг 1 не попал:
   написанный после шага 2 он уже не защищает — защита «до кода» к тому моменту снята.
2. **`changes_from` → таблица.** Диагноз подтверждён, работа механическая.
3. **`__post_init__` — только извлечение методов по смыслу**, без слияния шести
   правил в одно. ⚠️ Парную проверку `trailing_start` против `trailing_offset`
   извлекать **методом на `self`**, а не свободной функцией с двумя позиционными
   `float`: на месте вызова аргументы можно переставить, и это тот же класс дефекта,
   что мутация 5, только незаметнее. Цель — читаемость и падение сложности, насколько выйдет **без
   стирания различий**. Число не назначается заранее: назначенное число исполнитель
   начнёт добивать, а добивать здесь можно только слиянием денежных асимметрий.
