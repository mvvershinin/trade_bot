# Прототип: эталонное поведение торгового модуля №1

Модуль №1 — перенос действующего прототипа стратегии. Главный пункт приёмки ТЗ §9:

> Прогон на исторических данных в режиме «переворот через свечу» дал **те же сделки**,
> что действующий прототип; расхождения показаны **построчно**.

Этот документ описывает **поведение, которое надо воспроизвести**. Он самодостаточен:
всё, что нужно для реализации и для сверки, изложено здесь.

Сам прототип, эталонный датасет и оснастка для прогонов лежат в **локальном архиве
`reference/`** — он вне git и в поставку не входит. Состав и точные пути —
[`reference/README.md`](../reference/README.md), доступен только локально.

## 1. Параметры прототипа

Тринадцать параметров. Типы и умолчания важны: параметр с неверным типом
прототип принимает молча, без ошибки — и остаётся на своём умолчании,
то есть сверка идёт не с той конфигурацией, которую задавали.

| Параметр «Терминала» | Тип | По умолчанию у прототипа | Диапазон или список |
|---|---|---|---|
| Режим | строка из списка | выключен | выключен / реверс / только лонг / только шорт / только закрытие |
| Проскальзывание | число | `0` | 0–20 |
| Тип заявки | строка из списка | по рынку | по рынку / лимитная |
| Способ расчёта объёма | строка из списка | в контрактах | в контрактах / в валюте контракта / процент от депозита |
| Объём | число | `1` | 1–50 |
| Период средней | число | `15` | 5–300 |
| Тейк-профит, % | число | `0.5` | 0,1–5 |
| Стоп на день после тейка | булево | `true` | — |
| Начало торгового окна | время | `09:30` | — |
| Конец торгового окна | время | `11:30` | — |
| Закрывать в конце окна | булево | `true` | — |
| Торговля в выходные | булево | `false` | — |
| Актив портфеля для расчёта объёма | строка, произвольная | общая оценка портфеля | список значений не задан |

### Тринадцатый параметр — читается только при расчёте объёма от депозита

⚠️ Тринадцатый пропущен при первом разборе прототипа — там список был из двенадцати,
без последней строки. Счёт выправлен во всех документах проекта 30.08.2026
(`ROADMAP.md`, протокол сверки в скилле и в брифе аудитора).

Он влияет ровно на одну ветку — способ расчёта объёма «процент от депозита»:

- **умолчание** — процент считается от **общей оценки портфеля**;
- **любое другое значение** трактуется как **код инструмента**: процент считается
  от оценки позиции по этому инструменту в портфеле. Позиции с таким кодом нет →
  объём 0, запись об ошибке в лог и **сделки не будет**.

Это **свободная строка, а не список из двух значений**: набора допустимых значений
у параметра нет, прототип проверяет только совпадение с умолчанием. Дословное умолчание —
в таблице соответствия имён в архиве.

На эталонную конфигурацию (объём «в контрактах», 1 контракт) параметр не влияет:
в этом режиме он не читается вообще. Задавать явно нужно только там, где сверяется
расчёт объёма от депозита. Оба режима расчёта объёма кроме «в контрактах» опираются
ещё и на текущую лучшую цену и на состояние портфеля — воспроизводить их по свечам
нечем (§9).

⚠️ **Проскальзывание задаётся в шагах цены инструмента, а не в процентах** — несмотря
на знак процента в подписи поля у прототипа. Значение параметра умножается на шаг цены,
и результат прибавляется (вычитается) к цене **лимитной** заявки. При заявках «по рынку»
параметр не читается вовсе. В эталонной конфигурации он равен нулю, но при сверке
с ненулевым проскальзыванием единица измерения обязана совпадать с обеих сторон.

⚠️ **Нижняя граница тейка в объявленном диапазоне — 0,1, но значение 0 принимается**
при установке через программный интерфейс и означает «тейка нет» (§5). Два прогона
эталонного архива сделаны именно так. «Терминал» обязан уметь то же самое, иначе
конфигурации без тейка воспроизводить нечем.

⚠️ **Дословные имена параметров и значений списка в этот документ не выносятся** —
правило гигиены репозитория запрещает вызовы и идентификаторы чужого API в git.
Таблица соответствия «русское имя → дословное» лежит в локальном архиве рядом
с моделью прототипа и обязательна к прочтению перед прогоном сверки: имя нужно
буквальное, иначе параметр молча не применится.

⚠️ Умолчания **самого прототипа** (окно 09:30–11:30) не совпадают с умолчаниями **ТЗ**
(10:05–11:00). Цифры ТЗ — результат подбора, а не значения из кода.
При сверке параметры задаются явно с обеих сторон.

Чего в прототипе **нет**, а в ТЗ есть: выбор дней недели, интервалы паузы, скользящий тейк,
дневной лимит убытка, потолок объёма, проверка ГО, режим переворота «в одной свече».
Всё это — надстройка «Терминала», и сверять её не с чем.

## 2. Порядок обработки закрытой свечи

Точная последовательность. Порядок значим: перестановка шагов даёт другие сделки
при тех же настройках.

```
0.  свеча УЖЕ вошла в среднюю            ← до шага 1, вне этого списка
0.  время закрытия свечи = начало + таймфрейм ← фактически нужно до шага 1

1.  Режим == «Выключен»                  → выход
2.  свечей <= периода средней            → выход (прогрев индикатора)
3.  снимок открытых позиций              ← СНИМОК ДО ЗАКРЫТИЯ. Ключевая деталь
4.  время закрытия свечи = начало свечи + таймфрейм
5.  для каждой открытой позиции          → переставить тейк-профит
                                           позиция «закрывается» тейк НЕ получает
6.  вне окна ИЛИ нерабочий день:
        СНИМОК не пуст и «закрывать в конце окна»    → выход в деньги, без оглядки на среднюю
        СНИМОК не пуст и НЕ «закрывать в конце окна» → выход только по сигналу средней
        → выход из обработки в любом случае
        ⚠️ внутри обеих логик позиции с состоянием, отличным от «открыта», ПРОПУСКАЮТСЯ
7.  СНИМОК не пуст                       → логика закрытия по сигналу средней
                                           (внутри — тот же пропуск «не открытых»)
8.  Режим == «только закрытие»           → выход
9.  «стоп после тейка» И тейк был сегодня → выход
10. СНИМОК пуст                          → логика открытия
```

### Четыре уточнения к списку — внесены 30.08.2026 при написании движка

Список выше выглядел самодостаточным, но реализованный буквально давал другое
поведение. Всё проверено по исходнику прототипа.

**1. Позиция в состоянии «закрывается» пропускается — иначе в бою выйдет обратная сделка.**
Шаги 6 и 7 в прежней редакции читались «есть позиция → выход в деньги». Так написанная
реализация подаёт **повторную заявку на выход на каждой следующей свече вне окна**,
пока не пришла сделка. На истории это безобидно; в бою с рыночными заявками вторая
заявка после исполнения первой **открывает позицию в обратную сторону**.

В прототипе защита есть, и она в двух местах сразу: обе логики выхода перебирают
позиции и пропускают те, чьё состояние не «открыта». Перестановка тейка (шаг 5)
устроена так же — позиция в состоянии «закрывается» тейк не получает.

**2. Шаги 6, 7 и 10 спрашивают СНИМОК, а не текущее состояние.** Снимок берётся
один раз на шаге 3 и решает, **звать ли** логику. Сама логика внутри перечитывает
текущий список и фильтрует его по состоянию — то есть механизм двухуровневый.

Сегодня разницы нет, но это ровно то, что делает поведение в бою и на истории
одинаковым: при мгновенном исполнении рыночной заявки текущее состояние на шаге 10
окажется пустым, а снимок — нет, и вход в обратную сторону всё равно не подастся.
Реализация, спрашивающая на шагах 6, 7 и 10 текущее состояние вместо снимка,
на истории даст те же сделки, а в бою — другие.

**3. Шаги начинаются ПОСЛЕ того, как свеча вошла в среднюю.** Буквальное чтение списка
(режим проверяется первым, до счётчика свечей) говорит, что в режиме «Выключен» свеча
до индикатора не доходит. Это не так: у прототипа среднюю считает платформа, независимо
от режима и от всех десяти шагов. Десять минут в «Выключен» не меняют ни средней,
ни прогрева.

Отсюда требование к «Терминалу»: **свечи подаются в торговый модуль всегда**, режимом
фильтруется намерение, а не подача. Иначе выключение робота на десять минут изменит
список сделок.

**4. Шаг 4 — предусловие, а не шаг.** В исходнике присваивание времени закрытия
физически стоит четвёртым, поэтому нумерация здесь такая. Но время закрытия нужно
уже шагу 1 в любой реализации, где торговый модуль получает свечу со временем
закрытия — а «Терминал» требует именно этого. Воспроизводить позицию 4 буквально
не нужно: важен результат (`начало + таймфрейм`), а не место вычисления.

### Как заявка становится сделкой — исполнение по открытию следующей свечи

Десять шагов выше только **подают заявки**. Ни одна заявка не исполняется на той свече,
на закрытии которой подана.

```
заявка подана на закрытии свечи i
    → исполняется по цене `open` свечи i+1
    → временем сделки записывается ВРЕМЯ НАЧАЛА свечи i+1
```

Правило одно для входов и для выходов, и по сигналу средней, и по концу окна.
Единственное исключение — тейк-профит (§5): он срабатывает внутри свечи.

Проверено по журналу прототипа, 127 сделок подряд:

| Гипотеза цены исполнения | Расхождений из 127 |
|---|---:|
| **вход и выход по `open` следующей свечи** | **0** |
| выход по `close` сигнальной свечи | 47 |
| вход по `close` сигнальной свечи | 73 |
| уровень тейка считается от `close` сигнальной свечи | 108 |

Все 127 входов совпали с `open` свечи, чьё **начало** равно записанному времени входа
(восемь из них неразличимы: у этих свечей `open == close`). Выходы: 85 по `open` своей
свечи, 42 по уровню тейка, третьего варианта нет.

⚠️ Записанное время сделки равно **началу свечи исполнения**. На непрерывном ряде это
совпадает со временем закрытия сигнальной свечи, и на эталонном отрезке разрыва внутри
торгового окна нет ни одного — то есть две трактовки этим датасетом не различаются.
Реализовывать надо первую: начало свечи, по открытию которой прошла заявка.

⚠️ Если следующей свечи нет — заявка подана на последней свече отрезка, — сделки
не происходит: позиция либо остаётся открытой до конца прогона, либо не открывается вовсе.
Сводная статистика такую позицию приплюсовывает бумажной прибылью; закрытые сделки
берутся отдельно.

⚠️ **Та же позиция попадает и в счётчик прибыльных сделок**, если её бумажная прибыль
положительна. При сверке это выглядит расхождением на одну сделку там, где расхождения
нет. Замечено 30.08.2026 при сверке движка: архивный прогон «без окна, будни» даёт
1 211 сделок при одной оставшейся открытой и бумажной прибыли +425 ₽, и в колонке
прибыльных стоит 301 против 300 закрытых. Арифметика сходится точно, но механизм
**выведен из одного случая, а не доказан** — при следующей сверке проверить, не списывать
на совпадение.

### Почему переворот занимает две свечи

На шаге 3 берётся снимок позиций **до** закрытия. На шаге 7 подаётся заявка на выход,
но позиция ещё числится открытой (состояние «закрывается»). На шаге 10 проверка
«снимок пуст» не проходит — вход в обратную сторону не подаётся.

Дополнительно логика открытия **сама ещё раз** перечитывает список открытых позиций
и снова видит его непустым.

Заявка на вход в обратную сторону подаётся только на закрытии **следующей** свечи,
а исполняется — по правилу выше — на открытии свечи после неё:

```
свеча i    закрылась → снимок не пуст, подана заявка на выход
свеча i+1  открылась → выход исполнен,  время выхода = НАЧАЛО свечи i+1
свеча i+1  закрылась → снимок пуст,     подана заявка на вход в обратную сторону
свеча i+2  открылась → вход исполнен,   время входа  = НАЧАЛО свечи i+2
```

Между временем выхода и временем входа — **ровно один таймфрейм**, не «до пяти минут».
В эталонном журнале это 79 переворотов из 79 с разрывом ровно 5 минут, других значений нет.

Это и есть режим **«через свечу»**. Режим «в одной свече» (по умолчанию в ТЗ) —
поведение, которого у прототипа нет, и сверять его не с чем по построению.

## 3. Вход и выход: средняя и строгие неравенства

```
вход в лонг:    close  >  EMA        (если режим не «только шорт»)
вход в шорт:    close  <  EMA        (если режим не «только лонг»)
выход из лонга: close  <  EMA
выход из шорта: close  >  EMA
```

⚠️ **Шестое исключение из правила «всегда в позиции», не перечисленное в ТЗ §4.3.**
При `close == EMA` ровно: входа нет (оба неравенства ложны), выхода нет (позиция держится).
Если позиции не было — робот остаётся вне рынка на эту свечу.

На реальных ценах с шагом это редко, но не невозможно — особенно на инструментах
с крупным шагом цены и в узком боковике. Поведение «Терминала» в этой точке должно
быть выбрано осознанно и записано решением, а не унаследовано случайно.

⚠️ На эталонном отрезке `close == EMA` **не встречается ни разу** — 0 свечей из 10 878,
ближайший подход 0,017 пункта. Эту ветку данным датасетом не проверить в принципе.

### Средняя: по каким свечам считается и с чем сравнивается

**Считается по закрытиям всех свечей поданного ряда** — включая свечи вне торгового
окна, вечернюю сессию и выходные дни. Окно и запрет торговли в выходные ограничивают
только торговлю, на индикатор они не влияют, и на границе дня средняя не сбрасывается.
Отсюда следует, что и в конфигурации «выходные выключены» средняя всё равно посчитана
по выходным свечам, если они есть в поданных данных.

**Сравнивается закрытие свечи со значением средней, посчитанным включая эту же свечу.**
Не с предыдущим значением.

**Затравка — простая средняя по первым `период` закрытиям**, а не первое закрытие:

```
i <  период−1 :  средней ещё нет
i == период−1 :  среднее арифметическое закрытий с 0 по период−1
i >  период−1 :  E(i) = E(i−1) + 2/(период+1) * (close(i) − E(i−1))
```

Затравка первым закрытием даёт на эталонном отрезке **128 сделок вместо 127** и другое
время выхода уже на первой сделке. Различие живёт только в первом часе прогона, дальше
оба ряда сходятся, — поэтому ошибка выглядит как «разъехались первые сделки, дальше всё
хорошо», а не как систематический сдвиг. Именно поэтому её легко списать на прогрев.

### Неполные свечи — в прототипе про них нет ничего

Проверено по исходнику 30.08.2026: **ни одного упоминания** неполноты, незакрытости
или числа набранных минут. Свечи прототипу подаёт платформа, и вопрос там не возникает.

Для «Терминала» вопрос возникает: свеча собирается из минуток, и минутки могут прийти
не все. Выброшенная неполная свеча **не входит в среднюю и сдвигает прогрев** — то есть
меняет список сделок. Приняв её, мы считаем среднюю по огрызку.

**Это не пробел документа, а открытый вопрос**: у прототипа ответа нет и быть не может.
Умолчание «Терминала» — принимать неполную свечу: так ряд движка совпадает с рядом,
который получал прототип от платформы. Решение принято при Э1-7 и подлежит
подтверждению или отмене, а не воспроизведению.

⚠️ **Отброшенная свеча всё равно даёт сделку — и это решено осознанно 30.08.2026.**
Исполнитель спрашивается на **каждой** свече из источника, включая отброшенные:
неполную при включённой настройке и незакрытую.

Настройка «пропускать неполные свечи» относится к **ряду для индикатора и решений**,
а не к исполнению. Торги в интервале шли; неполна была наша сборка, а не рынок.
Заявка, поданная на прошлой свече, физически исполняется по первой цене этого интервала.
Не спросить исполнителя значило бы **отложить известие о сделке из-за качества нашей
агрегации** — а у боевой реализации это «отдай, что пришло от брокера», и сделка там
уже произошла.

Журнал обязан говорить обе вещи сразу: свеча не войдёт ни в среднюю, ни в прогрев —
и сделки, случившиеся к её началу, движок принимает. Умолчание одной из половин
превращает правдивую строку в обманчивую.

### Прогрев считается от начала поданного отрезка

Шаг 2 отбрасывает свечу, пока **число накопленных свечей ≤ периода средней**. Счёт идёт
от первой свечи, поданной на прогон, а не от начала файла с данными: предыстории
прототипу не подаётся.

```
свеча №(период+1) от начала отрезка → первая, на закрытии которой возможен сигнал
свеча №(период+2)                   → самая ранняя возможная сделка
```

Проверено на эталонном отрезке: первая свеча начинается в 08:55, период 15, значит
сигнал возможен на закрытии 16-й свечи (начало 10:10, закрытие 10:15). Первый вход
в журнале прототипа записан на 10:15 — открытие 17-й свечи. Сходится точно.

⚠️ Тот же датасет, поданный с более ранней границы (с 01.06 вместо 19.06), даёт
на общем участке **другой список сделок целиком**: к 19.06 средняя приходит уже
прогретой. Отрезок при сверке должен совпадать **до свечи**, а не «примерно тот же
период».

## 4. Торговое окно — по времени закрытия свечи, строго внутри

```
now = час*60 + минута  (от времени ЗАКРЫТИЯ свечи)
start == end            → окно не задано, торгуем весь день
start <  end            → now > start && now < end
start >  end            → now > start || now < end   (окно через полночь)
```

⚠️ Неравенства **строгие**. Свеча, закрывшаяся ровно в 10:05, в окно **не попадает**.
При окне 10:05–11:00 на пятиминутках первая рабочая свеча — закрывшаяся в 10:10.
Расхождение в один знак здесь даёт разный список сделок.

⚠️ У свечи хранится только **начало**. Время закрытия получается прибавлением
таймфрейма. «Терминал» обязан считать так же, иначе окно сдвинется на одну свечу.

⚠️ **Секунды отбрасываются — и у свечи, и у границ окна.** Внесено 30.08.2026,
проверено по исходнику. Формула `час*60 + минута` берёт только часы и минуты:
поле секунд у момента не читается, у границ окна — тоже, хотя у параметра оно есть.

Следствие, которого не видно из формулы: свеча, закрывшаяся в **10:05:30**, — это
по-прежнему **граница**, а не «после границы», и в окно 10:05–11:00 она **не попадает**.
Естественная реализация на Python сравнением моментов целиком (`start < момент < end`)
даёт обратный ответ и другую сделку.

⚠️ **Эту ошибку эталонный датасет не поймает никогда:** секунды в данных биржи всегда
нулевые. Только чтением и только этой строкой.

⚠️ **Окно считается в московском времени.** В прототипе вопрос не возникает — свечи
приходят в биржевом времени, и час читается как есть. В «Терминале» свеча приходит
с часовым поясом и может прийти в UTC: чтение часа «как есть» сдвинет окно на три часа.
Сделки при этом останутся — просто станут другими, и расхождение будут искать
в стратегии. Второй случай, который эталонный датасет не показывает.

### Дни недели

Прототип умеет только «выходные или нет»: при выключенной торговле в выходные
исключаются суббота и воскресенье. Выбора конкретных дней недели (правка заказчика
п. 10 про понедельник–вторник) в прототипе **нет** — это надстройка «Терминала».

## 5. Тейк-профит

```
уровень = цена входа ± цена входа * (процент / 100)
уровень ОКРУГЛЯЕТСЯ ДО ЦЕЛОГО, половина — К ЧЁТНОМУ
тип заявки «по рынку» → стоп-маркет на уровне активации
тип заявки «лимит»    → лимит с проскальзыванием
процент <= 0          → тейка нет
```

Шесть свойств, которые надо повторить точно:

1. **Уровень считается от цены входа и не двигается.** Скользящего тейка в прототипе нет.

2. **Тейк переставляется на каждой закрытой свече** для каждой открытой позиции
   (шаг 5) и дополнительно сразу при открытии позиции. Уровень при этом тот же —
   переставление ничего не меняет, но означает, что заявка живёт всё время позиции.

3. **Тейк — единственное событие прототипа, срабатывающее внутри свечи.** Всё остальное
   решается только на закрытии. Это важно для тестера: модель исполнения обязана
   уметь срабатывание тейка внутри бара, иначе сделки разойдутся.

4. **Уровень округляется до целого, половина — к чётному** (банковское округление).
   Не до шага цены инструмента: на эталонном инструменте шаг 25, а уровни тейка
   в журнале прототипа сплошь вне этой сетки — 217 180, 231 452, 230 542.
   Проверено перебором режимов округления на тех же 127 сделках:

   | Как получен уровень | Расхождений из 127 |
   |---|---:|
   | **до целого, половина к чётному** | **0** |
   | до целого, половина вверх | 1 |
   | до целого, половина вниз | 2 |
   | до целого вниз, отбрасыванием | 21 |
   | без округления | 21 |
   | до шага цены 25 | 39 |

   Ровно на «половину» попадают 18 уровней из 127; три из них попали в сделки и различают
   гипотезы, причём **в обе стороны**: 217 180,5 прототип свёл к 217 180 (вниз),
   а 231 451,5 и 230 541,5 — к 231 452 и 230 542 (вверх). Именно эта пара направлений
   отличает округление к чётному от «всегда вниз» и «всегда вверх»; одного случая
   для такого вывода не хватило бы.

5. **Тейк вооружён уже на той свече, в которой позиция открылась.** Позиция открывается
   по `open` свечи (§2), и `high`/`low` этой же свечи уже проверяются на достижение уровня.
   Запрет срабатывания на «своей» свече даёт 3 расхождения из 127: в журнале прототипа
   есть три сделки, у которых **время входа равно времени выхода** — открылась и закрылась
   тейком внутри одной свечи. Всего тейков на этой конфигурации 42, то есть случай
   не экзотический: каждый четырнадцатый.

6. **Исполнение ровно по уровню.** Цена выхода по тейку в журнале равна рассчитанному
   уровню — не `close` свечи и не ближайшей цене из сетки шага. Гипотеза «тейк исполняется
   по `close` свечи» даёт 42 расхождения из 127, ровно по числу тейков. Достижение уровня
   считается по касанию: `high >= уровень` для лонга, `low <= уровень` для шорта.
   ⚠️ Касание против пересечения этим датасетом **не проверяется**: свечи, у которой
   экстремум ровно равен уровню, на отрезке нет ни одной, и строгое неравенство даёт
   те же 127 сделок. «По касанию» выбрано по смыслу стоп-заявки, а не по данным.

### «Стоп после тейка»

Дата тейка запоминается двумя путями: по событию активации тейка и по факту закрытия
позиции с признаком тейка. При включённой настройке новых входов в эту **дату** больше нет
(шаг 9). Сравнивается она с датой **времени закрытия** свечи — «начало + таймфрейм», —
а не с датой начала свечи.

Проверка идёт по календарной дате свечи, а не по торговой сессии. Для вечерней сессии
и окна через полночь это разные вещи — при появлении второго окна в «Терминале»
поведение надо определить явно.

⚠️ **Два пути записи меряют дату по-разному — уточнено сверкой 30.08.2026 после того,
как первая редакция этого раздела оказалась неверной.**

| | Что записывается | Какая это дата |
|---|---|---|
| Путь А — по событию активации тейка | время закрытия последней **обработанной** свечи | дата **закрытия** |
| Путь Б — по факту закрытия позиции с признаком тейка | время сделки | дата **начала** свечи исполнения |
| Сравнение на шаге 9 | время закрытия текущей свечи | дата **закрытия** |

**Где пути расходятся — не там, где здесь было написано.** Первая редакция утверждала,
что они расходятся на свече, пересекающей полночь. Это опровергнуто данными: в журнале
прототипа **21 сделка живёт ровно одну свечу** (первая — 19.06 10:15→10:20), а это
возможно только если исполнение отложенных заявок и внутрибарные проверки свечи идут
**до** события её закрытия. Значит в момент активации тейка поле «последняя обработанная
свеча» хранит закрытие **предыдущей** свечи, а на непрерывном ряде оно равно началу
текущей — то есть пути дают одну и ту же дату, включая полночь.

**Расходятся они после разрыва в ряде**, и в обратную сторону: путь А даёт **старшую**
дату, путь Б — новую. Проверено синтетическим рядом с ночным разрывом.

⚠️ **Для любого завершённого тейка действует путь Б.** Оба пути пишут в одну переменную;
путь А срабатывает по событию активации, путь Б — по факту закрытия позиции, то есть
**позже**. Побеждает записавший последним. Путь А может пережить путь Б только там,
где активация была, а закрытия не случилось, — это боевой случай, за портом.

**Отсюда требование к «Терминалу»: воспроизводить надо путь Б, и этого достаточно.**
Прежнее требование «воспроизводить оба пути вместе с асимметрией» снято как
невыполнимое и ненужное: события активации без закрытия наш контракт порта не даёт
намеренно ([решение 0008](decisions/0008-take-profit-port-contract.md)),
а во всех наблюдаемых случаях путь Б и есть действующее значение.

⚠️ На эталонных данных расхождение недостижимо и это замерено: из 42 тейков эталонной
конфигурации на первую свечу после разрыва не попал **ни один**; в конфигурации
«без окна», где позиция переживает ночь, из 49 тейков — тоже ни одного.

⚠️ **Поле одно, а не два — решено при Э1-7, 30.08.2026.** У прототипа оба пути пишут
в одну переменную, и побеждает записавший последним; сравнение на шаге 9 читает её одну.
Два поля потребовали бы **правила объединения, которого у прототипа нет**, и дали бы
другой список сделок на свече через полночь — ровно там, где пути расходятся.

На эталонной конфигурации разойтись они не могут: при включённом «закрывать в конце
окна» позиция не переживает ночь. При выключенном — могут, и это место **не проверено
ничем**: ни журналом, ни агрегатом архива. Прямо связано с открытым вопросом №10
(несколько окон в день): второе окно или окно через полночь делают расхождение
достижимым, и тогда поведение придётся объявить явно.

## 6. Комиссия

Окружение прототипа при управлении через программный интерфейс **не переносит комиссию
в журнал** — она считалась сбоку, рублей за контракт.

Опорная цифра замеров: **14 ₽ за контракт на сторону**.
ТЗ §4.4 Е задаёт источник иначе: биржевой сбор из карточки инструмента МосБиржи
плюс 1 ₽ брокеру за контракт. **При сверке комиссия должна быть одинаковой с обеих
сторон, иначе сравниваются не сделки, а тарифы.**

### Комиссия на список сделок не влияет

Прототип её не читает вообще: ни объём, ни условия входа и выхода от неё не зависят.
В эталонных прогонах она так и считалась — в самом прогоне тариф стоял нулевой,
а рубли за контракт умножались на число сделок уже в отчёте: 127 сделок × 2 стороны
× 14 ₽ = 3 556 ₽, и так во всех точках архива.

Следствие для сверки: **комиссия — единственная величина, которую можно менять,
не меняя список сделок**. Сделки совпали, а деньги нет — расходится комиссия, а не
логика. Сделки разошлись — комиссия ни при чём, искать надо в другом месте.

⚠️ Оговорка на будущее: независимость держится, пока объём задан **в контрактах**.
При расчёте объёма процентом от депозита комиссия уменьшает депозит, депозит меняет
объём, объём меняет результат — обратная связь появляется, и правило перестаёт
действовать. Эталонная конфигурация работает в контрактах, на ней оговорка не срабатывает.

⚠️ Замечено в архиве: за позицию, оставшуюся открытой на конце отрезка, оснастка
списывает комиссию **одной** стороны. В сводке это видно как «комиссия не делится
на удвоенное число сделок нацело» и мешает сравнивать чистую прибыль.

## 7. Протокол сверки

1. Комиссия, проскальзывание и все тринадцать параметров (§1) заданы **явно и одинаково**
   с обеих сторон. Умолчания не используются.
2. Режим переворота «Терминала» — **«через свечу»**.
3. Период — один и тот же отрезок одного и того же эталонного датасета.
4. Сравнение **сделка в сделку**: время входа, сторона, цена входа, время выхода,
   цена выхода, причина выхода, объём. ⚠️ Причины выхода в журнале прототипа нет —
   как её сравнивать и чего это стоит, см. §9.
5. Расхождения показываются **построчно**, а не агрегатом. Совпадение итоговой
   прибыли при разных сделках — это не совпадение, а совпадение двух ошибок.
6. Прогон повторяется после каждого изменения в `strategies/` или `engine/`,
   затрагивающего вход, выход, окно или тейк.

**Что расхождением не является:** режим «в одной свече», дни недели, интервалы паузы,
скользящий тейк, дневной лимит, потолок объёма, проверка ГО. Этого в прототипе нет.

**Что расхождением является всегда:** разное время или сторона входа, разная причина
выхода, разное число сделок в режиме «через свечу» при одинаковых параметрах.

## 9. Чем это подтверждено и что не подтверждено

Всё, что выше, восстановлено двумя способами: чтением исходника прототипа и обратным
расчётом по его сохранённому журналу сделок. Способы дают разную силу довода, и путать
их нельзя — от этого зависит, где искать причину при первом же расхождении.

**Подтверждено построчно: 127 сделок из 127, ноль расхождений.** Одна конфигурация —
окно 09:30–11:30, будни, период 15, тейк 0,5%, «стоп после тейка» включён, «закрывать
в конце окна» включён, объём 1 контракт, заявки по рынку, проскальзывание 0. Сравнивались
время входа, сторона, цена входа, время выхода, цена выхода. На этом стоят: исполнение
по открытию следующей свечи, затравка средней, округление уровня тейка, тейк на свече
открытия, прогрев от начала отрезка, границы окна и переворот через свечу.

**Подтверждено только парой чисел «сделок / прибыль».** Пять других конфигураций архива,
включая боевую (окно 10:05–11:00, выходные включены — 106 сделок, +12 876 ₽ валовыми).
Списка сделок для них не сохранилось: те прогоны писала версия оснастки, не выгружавшая
позиции в отчёт.

**Не подтверждено ничем — код пишется по описанию, а не по данным:**

| Место | Почему не проверено |
|---|---|
| `close == EMA` ровно | на 10 878 свечах отрезка такой свечи нет ни одной, ближайший подход 0,017 |
| Касание против пересечения уровня тейка | экстремум свечи ни разу не равен уровню ровно |
| Выходные сессии построчно | в единственном полном журнале выходных дней нет |
| Выключенное «закрывать в конце окна» | восстановлено по исходнику, данными не подкреплено; заодно не проверена дата «стопа после тейка» через ночь (§5) |
| Режимы «только лонг», «только шорт», «только закрытие» | то же |
| Расчёт объёма кроме «в контрактах» и объём кроме 1 контракта | то же; оба других режима опираются на текущую лучшую цену и на состояние портфеля, по свечам их не воспроизвести |
| Лимитные заявки и ненулевое проскальзывание | не воспроизводились: молча выдать неверный результат хуже, чем не выдать никакого |
| Правая граница отрезка | в архивном прогоне данные обрываются до торгового окна последнего дня, сделок там нет ни с той, ни с другой стороны — граница не задета |

⚠️ **Причина выхода — отдельный случай.** Протокол сверки (§7) требует сравнивать её
сделка в сделку, а в журнале прототипа такого поля нет. Косвенно восстанавливается
только тейк: цена выхода совпала с рассчитанным уровнем — значит тейк (42 случая из 127).
Разделить «выход по обратному сигналу» и «выход по концу окна» по журналу нельзя:
обе заявки исполняются одинаково, по `open` следующей свечи. Пока это поле не выгружено
из самого прототипа, «причина выхода» в отчёте сверки — вывод проверяющей стороны,
а не сверенная величина.

⚠️ **Про круговую проверку.** Неоспоримый оракул здесь один — сохранённый журнал самого
прототипа, те самые 127 строк. Всё, что вне их, сверяется с производной моделью, а модель
и торговый модуль «Терминала» пишутся по одному и тому же источнику: если обе стороны
прочитали его одинаково неверно, сверка сойдётся против неверного эталона. Сходимость
с моделью доказывает **согласованность**, а не правильность. Прогон самого прототипа
на боевой конфигурации всё равно нужен — он перестал быть блокирующим шагом, но не отменён.
