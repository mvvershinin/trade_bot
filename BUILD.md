# Сборка и запуск

Четыре разных читателя, четыре разных раздела:

* [**Запустить из исходников**](#запустить-из-исходников) — разработчику;
* [**Собрать портативную поставку**](#собрать-портативную-поставку) — тому, кто готовит файл для пользователя вручную;
* [**Выпустить релиз по тегу**](#выпустить-релиз-по-тегу) — как то же самое собирается и публикуется автоматически;
* [**Запустить готовую программу**](#запустить-готовую-программу) — владельцу счёта, у которого нет ни Python, ни консоли. Для Linux отдельно — [список системных библиотек](#запустить-готовую-программу-на-linux).

Установка окружения подробно — [`INSTALL.md`](INSTALL.md). Готовые файлы,
не выходя в консоль вообще, — вкладка **Releases** репозитория на GitHub.

## Запустить из исходников

Нужен **Python 3.12** и `uv`. Версии зависимостей закреплены в `uv.lock`,
поэтому установка воспроизводима:

```bash
uv sync --locked --all-groups
.venv/bin/python -m app.main
```

Откроется окно. Данные программа держит в папке `userdata/` рядом с собой
и заводит её сама при первом запуске.

### Ключи командной строки

Окно — не единственный способ; программа умеет работать и без него.

Полная справка — `.venv/bin/python -m app.main --help`.

| Ключ | Что делает |
|---|---|
| `--fetch MXZ6` | скачать историю инструмента и выйти |
| `--fetch-days N` | глубина загрузки в днях |
| `--fetch-since 2026-06-01` | загрузка с даты |
| `--fetch-market futures\|shares` | какой рынок качать |
| `--inspect MXZ6` | опись базы по инструменту: что есть, за какие дни, где дыры |
| `--runs [N]` | список прошлых прогонов из журнала |
| `--stream`, `--stream-class` | подключиться к живым котировкам |
| `--shot FILE` | сделать снимок окна в файл и выйти (проверка без монитора) |
| `--db FILE` | взять другую базу |
| `--symbol`, `--days`, `--until` | что и за какой период показывать |
| `--dark`, `--light` | тема окна |

⚠️ Для `--fetch` и `--inspect` **токен брокера не нужен**: история берётся
у Московской биржи, бесплатно и без авторизации. Токен нужен только живому
потоку и портфелю.

### Проверки

```bash
.venv/bin/ruff check .                          линтер
.venv/bin/mypy                                  типы
.venv/bin/pytest -m "not slow" -n auto -q       быстрый прогон, ~16 с
.venv/bin/pytest -n auto -q                     полный, ~31 с
```

⚠️ Быстрый прогон отсекает сверку с прототипом и запуск подпроцессов.
Перед правкой торговой логики — входа, выхода, окна, тейка, переворота —
гоняется **полный**.

Прогон безэкранный по построению: `DISPLAY` убирается в `conftest`, и машина
разработчика ведёт себя как сборочный контейнер без монитора. Окна во время
тестов открываться не должны; если открылось — это дефект, а не мелочь.

Те же три команды гоняет **CI на GitHub** при каждом push и pull request
в `dev`/`main` — `.github/workflows/ci.yml`, соглашение о ветках —
[`CONTRIBUTING.md`](CONTRIBUTING.md). Порог для `ruff`/`mypy` там держит
храповик (`tests/test_lint_ratchet.py`), а не требование нулевой находки.

## Собрать портативную поставку

Сборщик — **Nuitka standalone**. Он компилирует Python в C и линкует нативный
бинарь: загрузчика нет, архива с байткодом нет, для эвристик антивируса это
обычная программа. Замеренный эффект перехода с PyInstaller — с 11 срабатываний
из 60 до 1 из 60.

```bash
.venv/bin/python tools/build.py            обычная сборка
.venv/bin/python tools/build.py --with-web плюс QtWebEngine (веб-график)
.venv/bin/python tools/build.py --dry-run  только показать команду, не собирать
```

Результат — `build/main.dist/`, внутри исполняемый файл `Terminal`.

⚠️ **`--onefile` не используется ни при каких условиях.** Он тоже
самораспаковывается во временную папку и возвращает часть проблем
с антивирусами. Только `--standalone` — решение
[`0001`](.docs/decisions/0001-packaging-nuitka-portable.md).

⚠️ **Сборка идёт десятки минут.** Это нормально и платится один раз на релиз.
Разработчик запускает программу из исходников, а не пересобирает бинарь
на каждую правку.

### Windows

Собирается **через MinGW**, а не MSVC: иначе готовый файл потребует
«Распространяемый пакет Visual C++», и обещание «ничего не надо устанавливать»
перестанет быть правдой.

После `tools/build.py` запускается упаковщик:

```
.venv\Scripts\python.exe tools\windows_package.py
```

Он делает четыре вещи, и вторая важнее остальных:

1. копирует `build/main.dist` в `dist/Terminal` — имя `main.dist` названо
   по файлу точки входа и владельцу счёта ничего не говорит;
2. **удаляет `userdata/`**, если она осталась от прогонов на машине сборки:
   там настройки и, возможно, **файл с токеном** — попасть в поставку она
   не имеет права ни при каких условиях;
3. кладёт рядом `README.txt` и `Запустить.bat`;
4. архивирует `dist/Terminal` в `dist/Terminal-{версия}-windows-x86_64.zip`
   через `zipfile` стандартной библиотеки — не через `7z`: на `windows-latest`
   7-Zip больше не гарантирован предустановленным (`actions/runner-images#9361`,
   проверено 08.09.2026).

⚠️ Кодировки, на которых тут всё и ломается: `README.txt` — UTF-8 **с BOM**
и переводами строк CRLF, иначе «Блокнот» покажет кракозябры или одну строку;
`Запустить.bat` — UTF-8 **без BOM**, но первой строкой `chcp 65001`, потому что
BOM в начале `.bat` командный процессор пытается выполнить как команду.

Версия для пункта 4 (и для `--file-version`/`--product-version` внутри
`tools/build.py`) берётся из переменной окружения `TERMINAL_VERSION`,
по умолчанию `0.1.0`. Собирая релиз по тегу, её выставляет
[`.github/workflows/release.yml`](.github/workflows/release.yml) — см.
[«Выпустить релиз по тегу»](#выпустить-релиз-по-тегу).

### Linux

После `tools/build.py` — свой упаковщик, симметричный Windows:

```bash
.venv/bin/python tools/linux_package.py
```

Три вещи: копирует `build/main.dist` в `dist/Terminal`, **снимает
`userdata/`** (тот же довод, что на Windows — до 08.09.2026 под Linux
этого шага не было вовсе, и ничего не мешало ей доехать до архива),
архивирует в `dist/Terminal-{версия}-linux-x86_64.tar.gz`.

⚠️ **`tar`, не `zip`.** У zip нет гарантии сохранить unix-бит «исполняемый»
при распаковке — пользователь получил бы `Permission denied` на `./Terminal`
без объяснения, откуда оно взялось.

Результат — папка около **165 МБ**, архив (`tar.gz`) — около **61 МБ**
(замер 08.09.2026, сборка версии для теста, полный прогон `tools/build.py`
на локальной машине разработки; на `ubuntu-latest` не измерено — см. ниже).

**Нужный пользователю glibc — измерен, не предположен.** По каждому файлу
поставки (`Terminal` и всем `.so`) прогнан `objdump -T`, из всех строк
`GLIBC_x.y` взят максимум:

```bash
objdump -T build/main.dist/* 2>/dev/null | grep -oE 'GLIBC_[0-9]+\.[0-9]+' | sort -V | tail -1
```

Ответ (замер 08.09.2026, сборка на Linux Mint 22.2 / Ubuntu 24.04, glibc 2.39,
проверено также в чистом `docker run ubuntu:24.04`): **GLIBC_2.38**. Его
требуют сам бинарь `Terminal` и несколько скопированных системных библиотек
машины сборки (`_decimal.so`, `libcrypto.so.3`, `libsqlite3.so.0`,
`libreadline.so.8`, `libexpat.so.1`) — то есть верхняя граница задаётся
машиной, на которой собирали, а не чем-то специфичным для кода проекта.

⚠️ **Собрано на `ubuntu-latest`, не на старой LTS в контейнере.** Решение
владельца счёта 08.09.2026: вместо возни со старым glibc ради максимальной
совместимости — честный список того, что нужно пользователю (следующий
раздел). Из этого следует, что программа **не запустится** на системах
со старым glibc: Ubuntu 22.04 (glibc 2.35), Debian 12 «bookworm» (2.36).
Работает на Ubuntu 23.10+, Ubuntu 24.04 LTS, Debian 13 «trixie», Fedora 39+,
любом Arch (2.38 и новее — эти дистрибутивы дают). Если это станет реальной
жалобой пользователя — тогда возвращаться к сборке в контейнере со старой
базой (приём уже описан в `DESKTOP-2026.md` §2), не раньше.

Проверить свою версию glibc: `ldd --version | head -1`.

⚠️ Замер на настоящем `ubuntu-latest`-раннере GitHub, а не на локальной
машине/контейнере, — только после первого настоящего тега. Пока это
измерение на образе того же дистрибутива (`ubuntu:24.04`), не на самом
раннере — см. [«Выпустить релиз по тегу»](#выпустить-релиз-по-тегу).

### Сборка не сдаётся без прохода «пустая папка → запуск → кнопка → результат»

Правило записано ценой ночи чужого времени. Сборку однажды отдали со словами
«готово к ручному тестированию», ни разу не нажав главную кнопку: проверяли
из консоли, где этот путь не задействован. Кнопка загрузки истории не работала
вовсе — поток данных открывался только при уже существующей базе, а кнопка нужна
ровно для того, чтобы базу создать. Замкнутый круг, которого не увидел ни один
из 3400 тестов.

Что проверяется на самом деле:

```
чистая машина, Python убран, PATH урезан, пакета Visual C++ нет
пустая папка → запуск двойным щелчком → кнопка «Загрузить историю…» → свечи
```

Прогон из консоли, снимок с виртуального экрана и зелёный прогон тестов —
**три разные вещи**, и ни одна не заменяет готовый файл, запущенный так,
как его запустят.

## Выпустить релиз по тегу

Ручные шаги выше — для разработчика, который собирает файл у себя. Для
настоящего релиза, который получит владелец счёта или сторонний человек
из Releases, — отдельный workflow:
[`.github/workflows/release.yml`](.github/workflows/release.yml). Заведён
08.09.2026, разбор решений и того, что проверено, а что нет, —
[`.docs/packaging/packaging-expert-release-2026-09-08-*.md`](.docs/packaging/).

### Как это устроено

Триггер — **тег вида `v*`** (`v0.2.0`, не `push`/`pull_request` в ветку):
Nuitka на Qt идёт минуты-десятки минут, гонять это на каждый коммит нельзя
(решение [`0001`](.docs/decisions/0001-packaging-nuitka-portable.md)).

```
git tag v0.2.0
git push origin v0.2.0
```

Дальше без участия человека:

1. **`version`** — разбирает тег в номер версии (`v0.2.0` → `0.2.0`),
   проверяет, что это ровно X.Y.Z (три числа через точку). Не похоже —
   вся сборка останавливается сразу, а не собирает что-то с версией
   `0.1.0` по умолчанию.
2. **`test`** — быстрый прогон (`uv run pytest -n auto`, по опорным числам
   ~70 с) на `ubuntu-24.04`. Тег может стоять на коммите, который никогда
   не гонял обычный CI, — это дешёвая страховка перед тем, как тратить
   десятки минут на сборку под две платформы.
3. **`build-linux`** (`ubuntu-latest`) и **`build-windows`** (`windows-latest`)
   — параллельно. Каждый: `uv sync`, подставляет версию из тега в
   `pyproject.toml` (см. врезку ниже — зачем это отдельный шаг),
   `tools/build.py`, затем `tools/linux_package.py` или
   `tools/windows_package.py`, архив — как артефакт workflow (ещё не
   в Releases).
4. **`release`** — только если **обе** платформы собрались: скачивает
   оба архива, подставляет версию в заготовку текста
   ([`.github/RELEASE_TEMPLATE.md`](.github/RELEASE_TEMPLATE.md)),
   публикует релиз через `gh release create` штатным `GITHUB_TOKEN`
   (секретов заводить не пришлось).

Если одна платформа собралась, а другая упала — `release` не запускается
вовсе: `needs` в GitHub Actions не даёт начать джоб, если у него в списке
зависимостей есть провалившийся. Релиз с одной архитектурой из двух
не опубликуется молча.

### Откуда берётся версия — и почему это отдельный шаг, а не просто ключ Nuitka

`ui/version.py` — то, что видит владелец счёта в заголовке окна и в журнале
решений при каждом старте, — вызывает `importlib.metadata.version("terminal")`
литеральной строкой. Nuitka 4.1.3 умеет заметить такой вызов и подставить
результат константой **во время компиляции**, если в этот момент на машине
сборки установлен пакет `terminal` нужной версии. То есть ответ зависит от
того, что записано в `pyproject.toml` и что успел проиндексировать
`uv sync` **до** запуска Nuitka — не от ключей командной строки самой
Nuitka (`--file-version`/`--product-version` меняют только диалог
«Свойства файла» в Проводнике Windows, и это **другое число**).

Поэтому шаг «Версия — из тега в pyproject.toml» в обоих build-джобах:
переписывает версию в `pyproject.toml` (`tools/set_version.py`,
CRLF-безопасно — Windows-раннер иначе кладёт файл с `\r\n`, и
`sed`-подстановка с `$` в шаблоне на такой строке молча ничего не находит),
переустанавливает пакет (`uv sync --all-groups`) и **проверяет результат
тем же вызовом**, которым воспользуется Nuitka. Не совпало — сборка
останавливается с понятным сообщением, а не продолжает с неверной версией
в окне.

Найдено и проверено экспериментом 08.09.2026 (три пробные сборки,
литеральный вызов против вызова через переменную, версия из METADATA
против переустановки пакета) — подробности в отчёте.

### Сколько это идёт и что не проверено до первого тега

Замер на 12-ядерной машине разработки: полная сборка Linux — 261 с.
GitHub-раннеры дают меньше ядер, поэтому в `release.yml` стоит щедрый
запас (`timeout-minutes: 45` на джоб сборки), а не измеренное время.

⚠️ **Windows-джоб не проверен вживую ни разу** — у проекта нет машины
с Windows. `--mingw64 --assume-yes-for-downloads` в `tools/build.py` —
официально документированный способ Nuitka самой скачать MinGW64 при
отсутствии компилятора, не самодеятельность, но первый настоящий тег —
первая живая проверка, что это действительно так пройдёт на `windows-latest`.

**Если сборка на раннере упала** — куда смотреть:

| Где красное | Что искать |
|---|---|
| `version` | тег не в формате `vX.Y.Z` — поправить тег (`git tag -d`, перетегировать) |
| `test` | обычный прогон тестов сломан на этом коммите — чинить как любой красный CI, `TESTING.md` |
| `Зависимости (uv sync --locked --all-groups)` | тег стоит на коммите, где разошлись `pyproject.toml`/`uv.lock` — то же семейство находок, что было в `ci.yml` при заведении (см. `packaging-expert-ci-2026-09-07-1940.md` §0) |
| `Версия — из тега в pyproject.toml` | `FOUND != VERSION` в сообщении — метаданные пакета не подхватили новую версию; это тревожный сигнал именно о механизме версии, разбирать по врезке выше, не переподставлять руками |
| `Сборка Nuitka` (Windows) | первая живая проверка MinGW64/кодировок консоли — see warning выше; в логе шага будет видно, что именно упало |
| `Упаковка` | `tools/linux_package.py`/`tools/windows_package.py` не нашли `build/main.dist` — предыдущий шаг не собрался, смотреть его |
| `release` | оба архива собрались, но `gh release create` отказал — частая причина: тег уже опубликован как релиз (пересобрать под тем же тегом нельзя; удалить тег и релиз в GitHub UI, перетегировать) |

Повторный прогон одного и того же тега невозможен: `gh release create`
откажет, если релиз с этим тегом уже есть — это защита от того, чтобы
тег `v0.2.0` в Releases однажды означал не то, что в нём реально лежит.
Чтобы переделать релиз — удалить тег и локально, и на GitHub, удалить
черновик/релиз в интерфейсе Releases (если он успел создаться), и
запушить тег заново.

## Запустить готовую программу

Пользователю нужны только сама папка и, для живых котировок, токен.

```
Terminal/                     ← папка программы, копируется куда угодно
├── Terminal.exe              (Windows) или Terminal (Linux)
├── Запустить.bat             (Windows) ярлык для тех, кому так привычнее
├── README.txt                (Windows) что это и как запустить
├── examples/                 образцы: файл токена, наборы настроек
└── userdata/                 ← заводится сама при первом запуске
    ├── broker-token.json     токен (класть руками)
    ├── candles.sqlite3       свечи
    ├── settings.json         настройки
    └── logs/                 технический журнал
```

**Токен** — файлом `userdata/broker-token.json`. Образец и объяснение каждого
поля лежат рядом с программой, в `examples/`. Для всего, кроме боевой торговли,
достаточно токена «только чтение»: он даёт котировки, историю и портфель,
но заявку выставить не может.

⚠️ **Подписи кода у программы нет** — это принятое решение
([`0002`](.docs/decisions/0002-no-code-signing.md)). При первом запуске Windows
покажет предупреждение SmartScreen, и это ожидаемо. Репутация считается
по хешу файла, а не по разработчику, поэтому платится заново на каждый релиз.

⚠️ **Одна копия на папку данных.** Вторая копия не поднимется и скажет об этом
словами. Замок держит система на дескрипторе, а не сам файл: после аварийного
завершения или отключения питания просроченного замка не остаётся.

### Запустить готовую программу на Linux

В архив `Terminal-*-linux-x86_64.tar.gz` не входит копия системных
библиотек Qt — они уже стоят на любом Linux с рабочим столом, кроме
совсем голых серверных установок. Список ниже — не с потолка и не «на
всякий случай»: каждая строка добавлена по факту одной конкретной ошибки
запуска, замер 08.09.2026 на `ubuntu:24.04` (чистый контейнер, без единого
лишнего пакета), в два прохода:

* **без экрана** (`QT_QPA_PLATFORM=offscreen`) — 5 библиотек, тот же список,
  что уже был выверен для CI (`.github/workflows/ci.yml`):
  `libgl1 libegl1 libxkbcommon0 libglib2.0-0 libdbus-1-3`;
* **с настоящим окном** (`QT_QPA_PLATFORM=xcb`, реальный сеанс X11 через
  Xvfb — не офскрин) — этого мало: собранный `Terminal` падал на старте
  с сообщением про `xcb-cursor0`, а после её установки `ldd` по плагину
  `libqxcb.so` показал ещё четыре недостающие библиотеки. Плюс — то же
  самое статическим разбором (`ldd`) для Wayland-плагина Qt, вживую сеанс
  Wayland не поднимался (на машине измерения его нет, см. ограничение ниже).

Полный список для реального окна (X11 **и** Wayland):

```bash
sudo apt install libgl1 libegl1 libxkbcommon0 libglib2.0-0 libdbus-1-3 \
                  libxcb-cursor0 libxkbcommon-x11-0 libxcb-icccm4 \
                  libxcb-keysyms1 libxcb-xkb1 libwayland-cursor0 libwayland-egl1
```

Fedora:

```bash
sudo dnf install mesa-libGL mesa-libEGL libxkbcommon glib2 dbus-libs \
                  xcb-util-cursor libxkbcommon-x11 xcb-util-wm xcb-util-keysyms \
                  wayland
```

Arch:

```bash
sudo pacman -S mesa libxkbcommon glib2 dbus xcb-util-cursor libxkbcommon-x11 \
               xcb-util-wm xcb-util-keysyms wayland
```

⚠️ Команды для Fedora/Arch — по именам пакетов, предоставляющим те же
файлы `.so`, **не проверены запуском** (измерение было только на
`ubuntu:24.04`, где живёт `apt`). Если название пакета устарело или
разъехалось с текущим репозиторием дистрибутива — это находка, сообщите.

**Что видно, если библиотеки не хватает.** Окно не откроется, а в терминале,
из которого запущен `./Terminal`, будет ровно это (реально полученное
сообщение, не выдуманное):

```
qt.qpa.plugin: Could not load the Qt platform plugin "xcb" in "" even though it was found.
This application failed to start because no Qt platform plugin could be initialized.

Available platform plugins are: wayland-brcm, wayland-egl, wayland, linuxfb, offscreen, minimal, eglfs, vnc, xcb, minimalegl, vkkhrdisplay.
```

⚠️ **Если программу запустили двойным щелчком в файловом менеджере (не из
терминала), этого сообщения никто не увидит** — Qt не может показать
графическое окно с ошибкой именно потому, что не смог инициализировать ни
один платформенный плагин для окна вообще. Программа в этом случае просто
не появится, без единого признака. Это молчаливый отказ (`CLAUDE.md`,
правило 13) — находка этой задачи, не починенная в рамках неё: чинить
пришлось бы код программы, а не документацию и сборку. Задача сборки
и поставки не правит `BACKLOG.md` (файл занят соседней правкой на момент
находки) — запись туда осталась за координатором, находка названа
в отчёте задачи.

**Что дальше проверено на реальном окне** (не только на факте запуска):
после установки всех 12 пакетов `Terminal` открыл окно 1440×900 под Xvfb
(X11), создал `userdata/` рядом с собой с правами только владельцу
(`settings.json` — `0600`, `logs/` — `0700`) — то же поведение первого
запуска, что и при обычном запуске из исходников.

⚠️ **Живой сеанс Wayland не запускался.** Для Wayland проверка — только
статическая (`ldd` по каждому файлу плагина Qt, ищет `=> not found`), не
запуск в реальном Wayland-компоситоре: на машине измерения его нет.
Плагин `libqwayland.so` в сборке присутствует и его метаданные читаются
(это закрывает риск из `DESKTOP-2026.md` §2 — «падение только на
Wayland-машине» из-за отсутствия плагина целиком), но «плагин есть и все
его .so на месте» — не то же самое, что «реальная Wayland-сессия
открывает окно». Первая живая Wayland-проверка — из рук человека
с таким рабочим столом.

## Куда класть готовые файлы

**Не в репозиторий.** `build/` и `dist/` исключены в `.gitignore`, и это
намеренно:

* git хранит **каждую** версию навсегда и не сжимает бинарники дельтой:
  десять релизов по 165 МБ — это плюс 1,6 ГБ в истории у всех, кто клонирует;
* убрать их потом можно только переписыванием истории;
* GitHub отклоняет файл больше 100 МБ и предупреждает уже на 50.

Место для готовых файлов — **Releases**: вложения до 2 ГБ, в историю не попадают,
версионируются и снабжаются описанием.

⚠️ Исключение, которое иногда путают с этим: **вендоринг**. Библиотеки `.dll`
и `.so`, положенные в репозиторий намеренно, чтобы сборка воспроизводилась
без сети, — это другое и это законно. Наш случай не такой.
