# Установка окружения

Одна команда после разовой установки `uv`. Ставит **всё дерево зависимостей**
из `uv.lock` — прямые пакеты, транзитивные, обе группы (`dev`, `build`) — и
проверяет каждый файл по хешу при закачке. Число из `uv.lock` не меняется
молча: переустановка окружения не должна быть источником другого результата
прогона (см. `.docs/decisions/0001-packaging-nuitka-portable.md`).

## Один раз на машину — поставить uv

`uv` ставится в **своё отдельное окружение**, не в системный Python и не
в проектный `.venv`:

```bash
python3 -m venv ~/.local/uv-0.12.7
~/.local/uv-0.12.7/bin/pip install "uv==0.12.7"
~/.local/uv-0.12.7/bin/uv --version      # должно быть ровно 0.12.7
```

Дальше в командах ниже вместо `uv` вызывается `~/.local/uv-0.12.7/bin/uv`
(или на него делается ссылка в `~/.local/bin`).

Отдельное окружение — не вкус, а обход двух замеренных граблей:

- **`python -m pip install "uv==0.12.7"` в системный Python не работает.**
  Проверено 31.08.2026 на машине разработки (Ubuntu, Python 3.12.3):
  `error: externally-managed-environment` — PEP 668, у дистрибутива стоит
  `/usr/lib/python3.12/EXTERNALLY-MANAGED`. Совет из текста ошибки
  (`--break-system-packages`) не годится: он ломает системный Python ради
  инструмента сборки.
- **`uv` внутри проектного `.venv` удаляет сам себя.** `uv sync` вычищает
  из окружения всё, чего нет в `uv.lock`, а `uv` там быть и не должен.
  Проверено 31.08.2026: `uv sync --locked --all-groups --dry-run` на окружении
  с установленным `uv` отвечает `- uv==0.12.7` в списке на удаление.
  Проектный `.venv` при этом не трогается ничем лишним: тот же прогон
  на рабочем окружении оставил `pip` на месте и добавил ровно один пакет.

Флаг `--group` здесь не участвует, поэтому грабля из `pyproject.toml`
(«группы PEP 735 требуют pip >= 25.1, системный pip 24.0 отвечает
`no such option: --group` и про свою версию молчит») этих команд не касается:
она про `pip install --group ...` для самого проекта, а не про установку `uv`.
`pip` внутри свежесозданного `venv` на этой машине — 26.2.1, ограничение выполнено.

Версия `uv` дополнительно закреплена в `pyproject.toml` (`[tool.uv] required-version`):
если на машине стоит другая версия `uv`, команды ниже останавливаются явной
ошибкой («Required uv version... does not match the running version...»), а не
молча пересчитывают `uv.lock` иначе.

## Установка проекта — воспроизводимо, из lock-файла

```bash
uv sync --locked --all-groups
```

- `--locked` — не пересчитывает `uv.lock`, а проверяет, что он всё ещё совпадает
  с `pyproject.toml`; расхождение — ошибка команды, а не тихий пересбор
- `--all-groups` — ставит все три группы: `dev` (pytest), `build` (Nuitka)
  и `lint` (ruff, mypy), а не только группу по умолчанию
- Создаёт `.venv` рядом с `pyproject.toml`, если его нет

Проверено 31.08.2026 (перепроверка после добавления `qasync`): та же команда
в полностью отдельном временном каталоге (вне рабочей копии, без существующего
`.venv`) поставила **24 пакета** по хешам из `uv.lock`; собранный `terminal`
встал editable-пакетом на копию исходников; тесты запустились и прошли
(единственное падение в том прогоне — `tests/test_engine_modes.py`, дефект
`engine/`, воспроизводится и без `qasync`, к установке отношения не имеет).

Двадцать четвёртым пакетом стал `qasync` — без него [решение 0005](.docs/decisions/0005-concurrency-model.md)
не перезапускается: `httpx` и `websockets` живут только на его цикле событий.
Платформенные `tzdata` и `colorama` в списке отсутствуют — они помечены как
нужные только на Windows, и на Linux их корректно нет.

## Статическая проверка

Ставится той же командой (группа `lint`), версии закреплены в `uv.lock`:

```bash
.venv/bin/ruff check .          линтер
.venv/bin/mypy                  типы
.venv/bin/ruff format --diff    показать форматирование, НЕ применять
```

⚠️ `ruff format` без `--diff` не запускать: он переписал бы 74 файла из 160,
включая `engine/` и `strategies/`, а это требует прогона сверки с прототипом.
Отдельная задача, `ROADMAP.md` Э1-0б.

Прогон сейчас не зелёный — 536 находок у ruff и 168 у mypy на 01.09.2026.
Числа приведены, чтобы их можно было сравнить: выросли — значит добавили своё.

## Обновление версий — отдельная задача, не побочный эффект

```bash
uv lock -P <пакет>
```

Пересчитывает `uv.lock` для одного пакета: для прямой зависимости (например,
Nuitka) — после того как её пин в `pyproject.toml` осознанно поднят; для
свободной транзитивной (например, `numpy`) — без правки `pyproject.toml`.
Массовое `uv lock --upgrade` не используется без отдельной задачи с полным
прогоном `/backtest` и `/parity` — `pandas`/`numpy` считают числа отчёта,
молчаливое обновление меняет их без единого коммита-виновника. Та же причина,
по которой Nuitka не обновляется побочным эффектом `pip install -U`
(решение 0001).

## Как запустить программу

```bash
.venv/bin/python -m app.main
```

Запуск **только модулем**, из корня рабочей копии. `python3 app/main.py` кладёт
в путь поиска каталог `app/`, и `import market` падает с «No module named
'market'» — ошибка выглядит как «слоя не существует» и уводит искать не туда
(`.docs/ARCHITECTURE.md` §2).

Что делает программа сегодня: открывает окно, читает свечи из базы
(`userdata/`, путь назначает `market/paths.py`) и показывает **прогон робота
по истории** — тот же движок и тот же торговый модуль, что пойдут в бой,
на тех же портах. К брокеру она не подключается и заявок не подаёт: боевого
хода нет (Э1-5), и ни один из трёх предохранителей — потолок объёма, дневной
лимит убытка, запас свободных средств — в движке не сделан. Программа говорит
это строкой в журнале решений при каждом старте.

Полезные ключи:

| Ключ | Зачем |
|---|---|
| `--days N` | сколько последних дней истории показать и прогнать; `0` — всю |
| `--until 28.08.2026 11:05` | по какой момент показывать историю (время московское) |
| `--symbol MXU6` | какой инструмент брать из базы |
| `--db ФАЙЛ` | другая база свечей |
| `--shot вид.png` | сохранить вид окна в файл и выйти; работает без экрана |
| `--dark` | тёмная палитра вместо системной |

Ключи латиницей и **без кириллических псевдонимов**: `--дней` и остальные пять
русских ключей убраны 31.08.2026. Причина — [PEP 672](https://peps.python.org/pep-0672/)
и правило проекта «имена в коде латиницей» (`CLAUDE.md`); ключ командной строки —
такое же имя, как имя переменной. Эта таблица до 31.08.2026 обещала русские
ключи, которых в программе уже не было: команды из документации отвечали
`unrecognized arguments`.

Базы нет — окно всё равно откроется и скажет об этом строкой. Историю
программа пока не загружает сама: автозагрузка — это Э1-5.

Оформление окна без базы и без движка, на заготовленных данных:
`python3 tools/demo.py` (это не программа, а показ интерфейса).

## Чего это не проверяет

`uv.lock` фиксирует, что скачается и по какому хешу — не то, что Nuitka
действительно соберёт рабочий бинарь на этом наборе версий. Сборка
Nuitka × PySide6 × Python 3.12 под Windows и Linux проверяется отдельно,
прогоном сборки на чистой машине (решение 0001), а не составом lock-файла.
