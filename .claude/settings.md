# Правила работы Claude в проекте «Терминал»

## Порядок работы

```
Сложная задача → /orchestrate → план → подтверждение → агенты → /validate → /review
Торговая логика → /strategy → /parity → /validate → /review
Деньги, заявки  → /broker или /strategy → /risk → /validate → /review
Перед боем      → /go-live
```

## Actor–Critic обязателен после каждой задачи

```
исполнитель пишет код → code-critic ищет, чем сломать
   → нашёл: исполнитель правит, снова критик
   → не нашёл: готово
```

Критик, валидатор и офицер безопасности объявлены **read-only**: у них нет `Write`
и `Edit`. Это не просьба в промпте, а список прав от харнесса — они физически
не могут по-тихому поправить найденное и отчитаться об успехе.

**Не показывать результат пользователю без прохождения критика.**
Нашёл проблемы — исправить и перепроверить, не спрашивая «исправить?».

## Открытые вопросы блокируют код

Нет ответа заказчика в `.docs/decisions/` — код не пишем, зовём `/roadmap`.
Исключение: обе ветки всё равно понадобятся (как с моментом переворота).

## Деньги

- Разработка и тесты — **только на симуляции**
- Боевой токен в тестах не участвует никогда
- Токен в фикстуре запрещён даже выдуманный: следующий подставит настоящий
- Переход в боевой режим — явное действие владельца счёта после `/go-live`

## Команды

- Многострочные команды — в скрипт, не в одну строку
- При ошибке — искать решение, не повторять наугад
- Не угадывать поведение API брокера — читать документацию

## Отчётность

- **НЕТ ОПТИМИЗМУ** — только факты и проблемы
- **Критик перед отчётом** — реально ли работает то, что я говорю? Проверил ли сам?
- Не спорить с пользователем о качестве кода
- Без упоминаний AI в коде и коммитах

## Quality gates перед коммитом

⬜ `/validate` — PASS
⬜ `/review` — APPROVE
⬜ `/parity` — сошлось (если тронута торговая логика)
⬜ `/risk` — APPROVE (если тронуты деньги или токен)
⬜ Тесты проходят
⬜ Нет хардкода цифр, за которыми стоят замеры
⬜ Токен не утекает
