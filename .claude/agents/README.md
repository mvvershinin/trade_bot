# Команда агентов проекта «Терминал»

Мульти-агентная разработка настольной программы для автоматической торговли
на Московской бирже через API брокера БКС.

**Стек:** Python 3.12 · PySide6 (Qt 6) · TradingView Lightweight Charts · SQLite ·
httpx/websockets · pandas · Nuitka standalone (запасной путь сборки — PyInstaller;
отменена связка «PyInstaller + установщик Inno Setup», [решение 0001](../../.docs/decisions/0001-packaging-nuitka-portable.md))
**ТЗ:** [`.docs/SPEC.md`](../../.docs/SPEC.md) · **Домен:** [`.docs/DOMAIN.md`](../../.docs/DOMAIN.md)

Собрано по образцу [claude_starter_pack](https://github.com/mvvershinin/claude_starter_pack):
роли в `agents/`, вызов через скиллы, правила исполняет харнесс хуками, а не модель.

---

## Обязательные правила

### 1. Сложные задачи — через координатора

Больше трёх файлов, новая фича, рефакторинг:

```
/orchestrate
```

### 2. После любого изменения кода

```
/validate     слои и зависимости
/review       баги и режимы отказа
```

### 3. Тронул торговую логику — сверься с прототипом

```
/parity       вход, выход, окно, тейк, переворот
```

Изменение торговой логики без сверки не принимается. Совпадение итоговой прибыли
при разных сделках — это не совпадение, а совпадение двух ошибок.

### 4. Тронул деньги — аудит предохранителей

```
/risk         заявки, объём, ГО, токен
```

### 5. Перед боевым режимом

```
/go-live      полный чеклист допуска к реальным деньгам
```

Три роли контроля объявлены **read-only** — критик не чинит то, что ревьюит.

### Как выбрана модель — правка 03.09.2026

Критерий один: **может ли ошибка в этой роли быть тихой и дорогой.** Громкая
ошибка — сборка не собралась, тест упал — стоит времени. Тихая — журнал,
который врёт в меньшую сторону; сторож, который не падает; нарушение слоя,
которое всплывёт через месяц — стоит денег на счёте.

Три роли подняты до opus, и повод не теоретический:

* **data-expert** — пишет слой с журналом-свидетельством и сторожами базы.
  03.09.2026 нашёл, что миграция уносит журнал каскадом (31 160 решений → 0)
  и что пересборка таблицы не даёт программе открыть свою базу ни разу.
  Обе находки — пробой, а не рассуждением. По прежней записи он шёл бы
  на sonnet;
* **architecture-validator** — единственная роль, проверяющая главное правило
  проекта. Пропущенное нарушение здесь и есть тот дефект, ради недопущения
  которого проект устроен;
* **test-expert** — пишет сторожей. 03.09.2026 трижды выяснилось, что
  зелёный тест не значит ничего: сверка 127 из 127 остаётся зелёной при
  снятой проверке принадлежности уровня. Отличить сторожа от декорации —
  рассуждение о мутации, а не сопоставление образцов.

Две роли **осознанно оставлены на sonnet**, чтобы это не читалось как недосмотр:

* **packaging-expert** — ошибки сборки громкие: не собралось, не запустилось.
  ⚠️ Пересмотреть, когда дойдёт до поставки на чужую машину: «не запускается
  у владельца счёта» — уже тихая ошибка, обнаруженная в худший момент;
* **product-owner** — пишет документы и приёмку, кода не трогает.

⚠️ **Отметка о причине правки.** До 03.09.2026 запись в брифах расходилась
с тем, как роли запускались: координатор переопределял модель в каждом вызове
и почти везде ставил opus. То есть таблица описывала не то, что происходит.
Расхождение опасно тем, что переопределение — решение одного вызова, а бриф
читают как правило: другой координатор запустил бы data-expert на sonnet
по написанному.

## Архитектура проекта

Зависимости строго в одну сторону, циклов нет:

```
market/         →  ничего            данные: ISS, таймфреймы, SQLite
broker/         →  ничего            БКС: токены, заявки, портфель
strategies/     →  ничего            сменные торговые модули
engine/         →  strategies/       свечи → сигнал → заявка → позиция
                →  два порта: источник свечей, исполнитель заявок
backtest/       →  engine/, strategies/, market/
ui/             →  engine/, backtest/, market/
app/            →  все
```

**Главное правило, ради которого всё построено:**

> Движок не знает, **откуда пришла свеча** — от брокера или из базы.
> Движок не знает, **какая стратегия** внутри.
> Стратегия не знает, **какой у нас брокер**.

Следствие: расхождение между тестером и боем невозможно по построению.
Разойтись могут только цены исполнения — и именно их показывает наложение
прогноза на факт.

**Два порта движка** — единственное место, где боевой режим и тестер расходятся:

| Порт | Бой | Тестер |
|---|---|---|
| Источник свечей | поток брокера + догрузка | чтение из SQLite |
| Исполнитель заявок | заявки в API БКС | модель исполнения с комиссией и проскальзыванием |

## Схемы работы

### Актёр и критик

```
исполнитель пишет код → code-critic ищет, чем сломать
   → нашёл: исполнитель правит, снова критик
   → не нашёл: готово
```

### Изменение в торговой логике

```
parity-auditor (прогон ДО) → strategy-quant → parity-auditor (прогон ПОСЛЕ)
   → расхождения построчно → architecture-validator + code-critic
```

Пропуск первого шага обесценивает всё остальное.

### Изменение, влияющее на числа в отчёте

```
backtest-methodologist (замер ДО) → исполнитель → замер ПОСЛЕ тем же протоколом
```

Относится и к изменениям, которые «не должны ничего менять»: рефакторинг,
оптимизация скорости, замена библиотеки. Особенно к ним.

### Новая фича

```
product-owner (нет ли открытого вопроса) → coordinator → исполнители
   → test-expert → architecture-validator + code-critic (параллельно)
```

### Работа с деньгами

```
trading-business-expert (что это значит в рублях) → исполнитель
   → risk-security-officer (предохранители на месте) → code-critic
```

## Хуки — правила исполняет харнесс, а не модель

| Хук | Событие | Что делает |
|---|---|---|
| `on-every-message.sh` | UserPromptSubmit | Напоминает шесть правил в каждом сообщении |
| `live-trading-guard.sh` | PreToolUse: Bash | **Блокирует** команды с боевым режимом, токеном брокера в окружении, чтением файла секрета и прямыми вызовами торгового API |
| `docs-reminder.sh` | PostToolUse: Edit\|Write | Подсказывает, какую документацию проверить, по затронутому слою |
| `check-critic.sh` | Stop | **Блокирует** завершение сессии, если код изменён после последнего критика |

`check-critic.sh` доработан против исходного стартер-пака: там хук видел только
`Edit`/`Write`/`NotebookEdit`, и файл, записанный через `sed -i` или heredoc,
проверку обходил молча. Здесь разбираются и вызовы `Bash`. Правки в `.claude/`,
`.docs/` и `reference/` кодом не считаются.

Отключить всё: `"disableAllHooks": true` в `settings.local.json`.
