# Как вносятся правки

Коротко, потому что коротко и есть весь процесс: правок со стороны пока
не бывает, а описан он для того, чтобы GitHub показывал его сам — при
открытии issue и pull request — и чтобы он был записан где-то, кроме
памяти одного человека.

## Ветки

```
dev      рабочая. Все правки — сюда.
main     релизная. Попадает в неё только через pull request из dev.
```

Прямой push в `main` не используется. `dev` может быть красным между
задачами — красным не имеет права быть только то, что уже дошло до `main`.

## CI

GitHub Actions гоняется на `push` и на `pull_request` в обе ветки —
`.github/workflows/ci.yml`. Что именно проверяется, на чём это проверено
и чего первый прогон ещё не подтвердил — в
[`.docs/packaging/packaging-expert-ci-2026-09-07-*.md`](.docs/packaging/).

Коротко, что должно быть зелёным перед тем, как просить слияние в `main`:

* тесты (`pytest`) — обязаны пройти; если сверка с прототипом пропущена
  (её тесты пропускаются без каталога `reference/`, а он в репозиторий
  не входит намеренно — см. `CLAUDE.md`, «Гигиена репозитория»), CI прямо
  говорит об этом в сводке прогона, а не молчит;
* `ruff`/`mypy` — не обязаны быть зелёными (см. `BUILD.md`, «Проверки»:
  на 07.09.2026 это 575 и 190 находок, разобранный остаток), но не имеют
  права **вырасти** против порога в `tests/test_lint_ratchet.py`. CI
  печатает текущие числа отдельными шагами; падает прогон не от них,
  а от храповика.

## Локально — то же самое, только раньше

```bash
uv sync --locked --all-groups
.venv/bin/ruff check .
.venv/bin/mypy
.venv/bin/pytest -n auto
```

Полный набор команд, замеры времени и что где смотреть при красном
прогоне — [`.docs/TESTING.md`](.docs/TESTING.md) и [`BUILD.md`](BUILD.md).
